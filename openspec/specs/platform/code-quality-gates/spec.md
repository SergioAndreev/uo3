# platform/code-quality-gates Specification

## Purpose

Определяет автоматизированные ворота качества кода, правовой чистоты и безопасности репозитория UO3: пороги тестового покрытия, стандарт сообщений коммитов Conventional Commits, управление версиями через Changesets, автоматизацию обновлений зависимостей через Renovate, контроль лицензий и уязвимостей, а также технический запрет проприетарных ассетов Ultima Online (ADR-002).

## Requirements

### Requirement: Пороги покрытия тестами по слоям монорепозитория
Запуск тестов с измерением покрытия MUST проверять минимальные пороги по слоям и завершаться с ненулевым кодом возврата при их снижении: для критических общих пакетов (`packages/domain`, `packages/rules`, `packages/protocol`, `packages/config`) не ниже `85%` строк/инструкций и `80%` ветвлений; для остальных приложений и runtime-пакетов не ниже `70%` строк/инструкций и `65%` ветвлений.

#### Scenario: Соблюдение порогов покрытия во всех слоях
- **WHEN** выполняется сбор покрытия для `packages/config` с покрытием `90%` строк и `85%` ветвлений
- **THEN** проверка порогов покрытия завершается с кодом возврата `0`

#### Scenario: Падение ниже порога покрытия в критическом пакете
- **WHEN** покрытие ветвлений в `packages/config` снижается до `75%` (ниже порога `80%`)
- **THEN** тестовый прогон завершается с ненулевым кодом возврата
- **AND** отчёт явно указывает пакет, метрику `branches`, фактическое значение `75%` и требуемый минимум `80%`

#### Scenario: Исключение сгенерированных файлов из расчёта покрытия
- **WHEN** в пакете присутствуют сгенерированные файлы объявлений типов или тестовые фикстуры `packages/test-kit`
- **THEN** они не искажают расчёт порогов покрытия производственного кода

### Requirement: Соблюдение формата Conventional Commits
Все сообщения коммитов (и заголовок PR при слиянии squash) MUST соответствовать стандарту Conventional Commits 1.0 (`<type>(<optional-scope>): <subject>`) с разрешённым набором типов (`feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`), длиной заголовка ≤ `100` символов и непустым описанием, проверяясь локально и в CI.

#### Scenario: Валидный коммит с областью пакета или фазы
- **WHEN** разработчик создаёт коммит с сообщением `feat(config): add typed server env validation` или `docs(p00): update bootstrap instructions`
- **THEN** проверка сообщения коммита завершается с кодом возврата `0`

#### Scenario: Отклонение неструктурированного или слишком длинного сообщения
- **WHEN** коммит имеет сообщение `fix bug` или заголовок длиной `120` символов
- **THEN** локальный git-хук и проверка CI завершаются с ненулевым кодом возврата с указанием нарушенного правила формата

#### Scenario: Допуск автоматических коммитов слияния и отката
- **WHEN** в ветке присутствует стандартный коммит `Revert "..."` или сгенерированный релизный коммит `chore(release): version packages`
- **THEN** проверка коммитов пропускает его с кодом возврата `0`

### Requirement: Локальные пре-коммит проверки качества
Репозиторий MUST автоматически устанавливать git-хуки при установке зависимостей: на этапе `pre-commit` MUST проверяться форматирование и линтинг индексированных файлов, отсутствие проприетарных ассетов и утечек секретов (за ≤ `15` секунд на типовом коммите), а на этапе `commit-msg` MUST проверяться формат Conventional Commits.

#### Scenario: Быстрая проверка индексированных файлов перед коммитом
- **WHEN** разработчик индексирует 3 изменённых TypeScript-файла и выполняет `git commit`
- **THEN** хук проверяет только индексированные файлы, завершается успешно за ≤ `15` секунд и позволяет создать коммит

#### Scenario: Блокировка коммита с синтаксической ошибкой линтинга
- **WHEN** индексированный файл содержит запрещённый импорт или ошибку форматирования
- **THEN** хук `pre-commit` прерывает создание коммита с ненулевым кодом возврата до попадания кода в историю

#### Scenario: Гарантия проверки в CI при обходе локального хука
- **WHEN** разработчик обходит локальный хук флагом `--no-verify` и отправляет PR
- **THEN** аналогичные проверки в стадии `quality-gates` CI обнаруживают нарушение и блокируют PR

### Requirement: Управление версиями и журналом изменений через Changesets
Репозиторий MUST содержать конфигурацию Changesets для семантического версионирования и ведения changelog; каждый Pull Request, изменяющий производственный код в `apps/*` или `packages/*`, MUST включать валидный файл changeset (или явную пометку отсутствия пользовательского релиза для изменений только тестов, документации или CI), что проверяется в CI.

#### Scenario: PR с производственным изменением и файлом changeset
- **WHEN** PR изменяет `packages/config/src/` и добавляет валидный markdown-файл в `.changeset/` с типом изменения (`patch`/`minor`/`major`)
- **THEN** проверка статуса changeset в CI завершается с кодом возврата `0`

#### Scenario: PR с изменением производственного кода без changeset
- **WHEN** PR изменяет `packages/db/src/` и не содержит файла changeset и освобождающей метки
- **THEN** проверка changeset в CI завершается с ненулевым кодом возврата и инструкцией генерации файла changeset

#### Scenario: PR затрагивающий только документацию или спецификации
- **WHEN** PR изменяет исключительно файлы `docs/**` или `openspec/**`
- **THEN** проверка changeset завершается успешно без требования добавления файла changeset

### Requirement: Автоматизация обновлений зависимостей (Renovate)
Репозиторий MUST содержать валидируемую конфигурацию Renovate, которая группирует minor/patch-обновления по экосистемам (инструменты TypeScript, серверный стек, клиентский стек, GitHub Actions, образы Docker), задаёт период стабилизации `minimumReleaseAge` ≥ `3` дней для обычных обновлений, пиннит дайджесты/SHA для Actions и Docker, отделяет major-обновления и ограничивает число одновременных PR ≤ `5`.

#### Scenario: Валидация схемы конфигурации Renovate
- **WHEN** выполняется проверка конфигурации Renovate в стадии `quality-gates`
- **THEN** конфигурация проходит официальную валидацию схемы без ошибок и устаревших опций
- **AND** подтверждаются параметры `minimumReleaseAge >= 3 days` и `prConcurrentLimit <= 5`

#### Scenario: Немедленные security-обновления без задержки стабилизации
- **WHEN** публикуется исправление уязвимости безопасности (security advisory)
- **THEN** политика Renovate разрешает создание PR с исправлением без ожидания 3-дневного периода стабилизации

### Requirement: Белый список лицензий сторонних зависимостей
Автоматическая проверка MUST анализировать полное дерево разрешённых зависимостей против белого списка SPDX (`MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `0BSD`, `CC0-1.0`, `Unlicense`, `MPL-2.0`, `Zlib`, `BlueOak-1.0.0`, `Python-2.0`) и падать с ненулевым кодом при copyleft (`GPL`, `AGPL`, `SSPL`), проприетарной или `UNKNOWN` лицензии без исключения.

#### Scenario: Чистое дерево зависимостей по белому списку SPDX
- **WHEN** запускается проверка лицензий `check:licenses` на монорепозитории
- **THEN** все зависимости соответствуют белому списку SPDX или явно задокументированному исключению
- **AND** команда завершается с кодом возврата `0`

#### Scenario: Обнаружение зависимости под лицензией AGPL или с неизвестной лицензией
- **WHEN** в дерево зависимостей попадает пакет с лицензией `AGPL-3.0-only` или `UNKNOWN`
- **THEN** команда `check:licenses` завершается с ненулевым кодом возврата
- **AND** выводит имя пакета, версию, обнаруженную лицензию и цепочку зависимостей

### Requirement: Аудит безопасности зависимостей и контроль цепочки поставок
Автоматический аудит зависимостей в CI MUST блокировать сборку при наличии уязвимостей уровня `critical` или `high` в производственных зависимостях, если для них отсутствует задокументированное временное исключение со сроком действия ≤ `30` дней, а конфигурация пакетного менеджера MUST запрещать произвольное выполнение postinstall-скриптов сторонних пакетов вне явного белого списка.

#### Scenario: Отсутствие критических и высоких уязвимостей
- **WHEN** выполняется проверка аудита зависимостей на зафиксированном lockfile
- **THEN** при отсутствии непокрытых исключениями уязвимостей уровней `critical` и `high` проверка завершается с кодом возврата `0`

#### Scenario: Просроченное исключение уязвимости
- **WHEN** в файле аудита присутствует временное исключение (waiver) с датой `expiresAt` в прошлом
- **THEN** проверка безопасности зависимостей завершается с ненулевым кодом возврата и требует обновления зависимости или пересмотра исключения

#### Scenario: Блокировка неавторизованного lifecycle-скрипта
- **WHEN** добавляется сторонняя зависимость с произвольным `postinstall` скриптом, не внесённая в белый список одобренных сборочных пакетов
- **THEN** менеджер пакетов не выполняет её скрипт автоматически без явного одобрения в корневой конфигурации

### Requirement: Запрет проприетарных ассетов Ultima Online в репозитории
Гейт правовой чистоты (`check:assets`, в `pre-commit` и CI) MUST блокировать проприетарные форматы UO (`.mul`, `.uop`, `.idx`, `.def`, `.enu`; имена `tiledata.*`, `verdata.*`, `hues.*`, `cliloc.*`, `art.*`, `anim*`, `multi.*` — кроме исходников и документации `.ts`/`.tsx`/`.js`/`.mjs`/`.json`/`.md`/`.yaml`), бинарники > `512` КиБ и медиафайлы без записи `CC0-1.0` или `synthetic-generated` в реестре ассетов (ADR-002).

#### Scenario: Блокировка попытки закоммитить проприетарный файл UO
- **WHEN** в рабочем дереве индексируется файл `map0.mul`, `artLegacyMUL.uop` или `tiledata.mul` в любой директории репозитория
- **THEN** проверка `check:assets` завершается с ненулевым кодом возврата и кодом нарушения `ERR_PROPRIETARY_UO_ASSET`
- **AND** указывает запрещённый путь и ссылку на политику ADR-002

#### Scenario: Исходный код с UO-подобным именем не блокируется
- **WHEN** индексируются файлы `packages/uo-formats/src/tiledata.ts`, `packages/rules/src/world/map-patch.ts` и `packages/uo-formats/docs/anim-multi.md`
- **THEN** проверка `check:assets` не сообщает `ERR_PROPRIETARY_UO_ASSET` и завершается с кодом возврата `0`

#### Scenario: Допуск задекларированной CC0-заглушки в реестре ассетов
- **WHEN** добавляется небольшой PNG-спрайт размером `12` КиБ в директорию заглушек с записью SHA-256 и лицензией `CC0-1.0` в манифесте происхождения ассетов
- **THEN** проверка `check:assets` проверяет совпадение хэша и завершается с кодом возврата `0`

#### Scenario: Блокировка крупного бинарного файла или незадекларированного медиа
- **WHEN** добавляется бинарный файл размером `800` КиБ или PNG-файл без записи в манифесте происхождения ассетов
- **THEN** проверка `check:assets` завершается с ненулевым кодом возврата с указанием причины (`ERR_BINARY_SIZE_LIMIT` или `ERR_UNDECLARED_ASSET`)

### Requirement: Обнаружение утечек секретов и статический контроль безопасности кода
Автоматическое сканирование репозитория в `pre-commit` и CI MUST блокировать коммиты с приватными ключами (`BEGIN ... PRIVATE KEY`), токенами API, строками подключения с реальными учётными данными и высокоэнтропийными секретами, а статический анализ клиентских пакетов MUST запрещать динамическое исполнение кода (`eval`, `new Function`, строковый `setTimeout`) согласно ADR-012.

#### Scenario: Блокировка приватного ключа или токена в исходном коде
- **WHEN** в любой отслеживаемый файл добавляется блок `-----BEGIN PRIVATE KEY-----` или токен формата GitHub/AWS
- **THEN** сканер секретов завершается с ненулевым кодом возврата и не выводит полное значение секрета в открытый лог

#### Scenario: Допуск шаблонных плейсхолдеров в .env.example
- **WHEN** в `.env.example` указаны документированные локальные заглушки разработки (например, `CHANGE_ME_LOCAL_DEV_ONLY`)
- **THEN** сканер секретов распознаёт разрешённые маркеры шаблона и завершается с кодом возврата `0`

#### Scenario: Блокировка eval в клиентском коде
- **WHEN** в файле `apps/client/src/` или `packages/ui-kit/src/` используется `eval(...)` или `new Function(...)`
- **THEN** статический анализ кода завершается с ненулевым кодом возврата
