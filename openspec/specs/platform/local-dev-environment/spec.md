# platform/local-dev-environment Specification

## Purpose

Определяет локальное окружение разработки UO3 на базе контейнеров для PostgreSQL 17, Valkey 8, NATS JetStream и стека наблюдаемости Grafana, а также скрипты инициализации (`bootstrap`), наполнения тестовыми данными (`seed`), сброса и диагностики (`doctor`). Позволяет любому разработчику или ИИ-агенту поднять рабочую инфраструктуру за ≤ 10 минут одной командой.

## Requirements

### Requirement: Композиция базовых инфраструктурных сервисов
Конфигурация Docker Compose MUST объявлять базовый профиль (`core`) с сервисами PostgreSQL 17 (порт по умолчанию `5432`), Valkey 8 (`6379`) и NATS 2.10+ с включённым JetStream (`4222` клиентский, `8222` мониторинг), использовать зафиксированные версии образов без тега `latest`, именованные тома данных и активные healthcheck-пробы с интервалом ≤ `10` секунд.

#### Scenario: Поднятие базового инфраструктурного стека
- **WHEN** разработчик запускает базовый профиль Docker Compose на чистом хосте с доступным Docker Engine
- **THEN** контейнеры PostgreSQL 17, Valkey 8 и NATS JetStream переходят в состояние `healthy` за ≤ `60` секунд после загрузки образов
- **AND** HTTP-эндпоинт мониторинга NATS подтверждает активный режим JetStream

#### Scenario: Сохранение данных при перезапуске контейнеров
- **WHEN** разработчик останавливает и повторно запускает контейнеры базового профиля без удаления томов
- **THEN** данные в PostgreSQL 17 и потоки JetStream сохраняются в именованных томах

#### Scenario: Проверка запрета плавающих тегов образов
- **WHEN** валидируется файл композиции контейнеров
- **THEN** ни один сервис не использует тег `:latest` или незафиксированный мажорный тег

### Requirement: Опциональный стек локальной наблюдаемости
Конфигурация Docker Compose MUST предоставлять отдельный профиль `observability` с OpenTelemetry Collector (`4317` gRPC, `4318` HTTP), Prometheus (`9090`), Loki (`3100`), Tempo (`3200`) и Grafana (`3000`), автоматически подключающий источники данных и базовый дашборд здоровья сервисов без ручной настройки в веб-интерфейсе.

#### Scenario: Запуск с профилем наблюдаемости
- **WHEN** разработчик запускает Docker Compose с активным профилем `observability`
- **THEN** все 5 сервисов наблюдаемости переходят в состояние `healthy` за ≤ `90` секунд после загрузки образов
- **AND** в Grafana автоматически зарегистрированы источники данных Prometheus, Loki и Tempo, а также базовый дашборд состояния локального стенда

#### Scenario: Запуск базового профиля без наблюдаемости
- **WHEN** разработчик запускает только базовый профиль без `observability`
- **THEN** контейнеры Grafana, Prometheus, Loki, Tempo и OTel Collector не создаются и не потребляют ресурсы хоста

### Requirement: Изолированная база данных для интеграционных тестов
Локальное окружение MUST обеспечивать выделенную базу данных `uo3_test` (изолированную от основной базы разработки `uo3_dev` на отдельном имени БД или порту `5433`), чтобы прогон интеграционных тестов и очистка таблиц не затрагивали данные локальной сессии разработчика.

#### Scenario: Автоматическое создание обеих баз при инициализации
- **WHEN** контейнер PostgreSQL 17 инициализируется на чистом томе
- **THEN** автоматически создаются базы `uo3_dev` и `uo3_test` с настроенными расширениями и правами роли разработки

#### Scenario: Прогон тестов без повреждения данных разработки
- **WHEN** в `uo3_dev` присутствуют пользовательские записи разработки и запускаются интеграционные тесты
- **THEN** тесты выполняются исключительно против `uo3_test`
- **AND** состояние записей в `uo3_dev` остаётся неизменным

### Requirement: Переопределение портов и предотвращение конфликтов хоста
Все пробрасываемые на хост порты сервисов Docker Compose MUST настраиваться через переменные окружения с документированными значениями по умолчанию, позволяя запускать стенд в нескольких рабочих копиях или при занятых стандартных портах на хосте.

#### Scenario: Смена портов через переменные окружения
- **WHEN** разработчик задаёт переопределённые порты `PG_PORT=15432`, `VALKEY_PORT=16379`, `NATS_PORT=14222` и запускает стек
- **THEN** сервисы становятся доступны на указанных портах и не пытаются занимать `5432`, `6379` и `4222`

#### Scenario: Диагностика занятого порта при старте
- **WHEN** порт `5432` уже занят другим процессом на хосте без переопределения `PG_PORT`
- **THEN** скрипт диагностики или `bootstrap` сообщает о конфликте порта `5432` и указывает переменную окружения для его переопределения

### Requirement: Однокомандный и идемпотентный bootstrap окружения
Скрипт `bootstrap` MUST за один запуск проверять пререквизиты (Node.js 22, менеджер пакетов, доступность Docker), устанавливать зависимости, создавать отсутствующие локальные `.env` файлы из шаблонов без перезаписи существующих, поднимать базовые контейнеры, ждать их готовности (таймаут ≤ `120` с), применять миграции и запускать `seed`, укладываясь в ≤ `10` минут и поддерживая безопасный повторный запуск.

#### Scenario: Первичный запуск bootstrap на чистом репозитории
- **WHEN** разработчик или ИИ-агент выполняет корневую команду `bootstrap` в свежесклонированном репозитории с установленными пререквизитами
- **THEN** скрипт завершается с кодом возврата `0`
- **AND** создаются отсутствующие `.env` файлы, все базовые контейнеры здоровы, миграции применены и базовый seed выполнен

#### Scenario: Повторный запуск bootstrap с пользовательскими настройками
- **WHEN** разработчик изменил локальный параметр в `.env` и повторно запускает `bootstrap`
- **THEN** существующий `.env` файл не перезаписывается
- **AND** миграции и `seed` выполняются идемпотентно без дублирования записей и с кодом возврата `0`

#### Scenario: Отказ при недоступном Docker Engine
- **WHEN** команда `bootstrap` запускается при остановленном Docker daemon
- **THEN** команда завершается с ненулевым кодом возврата в течение ≤ `10` секунд
- **AND** выводит явную инструкцию по запуску Docker вместо зависания до таймаута

### Requirement: Автоматические миграции схемы и идемпотентный seed
Команды `db:migrate` и `db:seed` MUST применять версионированные миграции схемы PostgreSQL и наполнять базу детерминированными стартовыми метаданными среды и тестовых фикстур идемпотентно: повторный запуск обеих команд на уже проинициализированной базе MUST завершаться с кодом `0` и оставлять идентичное состояние строк.

#### Scenario: Применение миграций и первичный seed на пустой БД
- **WHEN** на пустой базе `uo3_dev` последовательно выполняются `db:migrate` и `db:seed`
- **THEN** создаётся таблица учёта миграций и базовая таблица метаданных окружения
- **AND** `db:seed` записывает детерминированный набор стартовых записей и возвращает код `0`

#### Scenario: Повторный запуск db:seed
- **WHEN** команда `db:seed` запускается второй раз подряд на той же базе
- **THEN** команда завершается с кодом возврата `0` без ошибок нарушения уникальности
- **AND** количество записей и их значения в базе не изменяются

### Requirement: Чистый сброс локального окружения
Скрипт сброса окружения (`env:reset`) MUST полностью пересоздавать базы данных разработки и тестов (либо тома Docker), повторно применять миграции и `seed`, и MUST блокировать выполнение против нелокальных хостов БД (`host` не в `localhost`, `127.0.0.1`, `::1`, `postgres`), возвращая ненулевой код возврата.

#### Scenario: Успешный сброс локального стенда
- **WHEN** разработчик выполняет `env:reset` при подключении к локальной БД с флагом подтверждения `--yes`
- **THEN** временные локальные данные удаляются, миграции и `seed` применяются заново и команда завершается с кодом `0`

#### Scenario: Защита от сброса удалённой базы данных
- **WHEN** в `DATABASE_URL` указан удалённый хост (например, `prod-db.example.com`) и запускается `env:reset`
- **THEN** команда немедленно прерывается с ненулевым кодом возврата и ошибкой защиты от сброса нелокальной БД до выполнения любых разрушительных операций

### Requirement: Скрипт диагностики окружения (doctor)
Команда `doctor` MUST проверять версии Node.js 22 и менеджера пакетов, доступность Docker daemon, состояние контейнеров и занятость портов, валидность `.env` файлов и сетевую доступность PostgreSQL, Valkey и NATS, выводя структурированный отчёт по каждому пункту и возвращая ненулевой код возврата при отказе любой обязательной проверки.

#### Scenario: Диагностика здорового окружения
- **WHEN** все сервисы базового профиля запущены и конфигурация корректна, и выполняется `doctor`
- **THEN** отчёт помечает каждую обязательную проверку статусом `PASS` и команда завершается с кодом возврата `0`

#### Scenario: Диагностика при остановленном Valkey
- **WHEN** контейнер Valkey остановлен и выполняется `doctor`
- **THEN** проверка Valkey получает статус `FAIL` с указанием хоста/порта и команды запуска контейнера
- **AND** команда `doctor` завершается с ненулевым кодом возврата

### Requirement: Локальный запуск и проверка работоспособности каркасов приложений
Единая команда локального запуска (`dev`) MUST поднимать каркасы приложений (`apps/api`, `apps/game-server`, `apps/client`, `apps/admin`) с подключением к локальной инфраструктуре, а серверные приложения MUST предоставлять HTTP-эндпоинты `/healthz` (живучесть процесса) и `/readyz` (проверка живого подключения к PostgreSQL, Valkey и NATS с HTTP `200` при готовности и `503` при отказе зависимости).

#### Scenario: Проверка готовности серверных каркасов при здоровом стеке
- **WHEN** локальный стек и серверные каркасы `apps/api` и `apps/game-server` запущены, и выполняется `GET /readyz`
- **THEN** оба сервиса отвечают HTTP `200` с JSON-статусом `ok` и подтверждением подключения к PostgreSQL, Valkey и NATS за ≤ `500` мс

#### Scenario: Деградация readiness при потере подключения к NATS или БД
- **WHEN** сервис NATS останавливается во время работы `apps/game-server` и запрашивается `GET /readyz`
- **THEN** эндпоинт `/healthz` продолжает возвращать HTTP `200`, а `/readyz` возвращает HTTP `503` с указанием недоступной зависимости `nats`
