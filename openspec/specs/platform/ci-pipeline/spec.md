# platform/ci-pipeline Specification

## Purpose
Определяет конвейер непрерывной интеграции на базе GitHub Actions для проверки каждого Pull Request и основной ветки `main`: параллельные проверки линтинга, типизации, тестов с сервисными контейнерами, сборки и ворот качества, кэширование, публикацию артефактов, защиту цепочки поставок CI и политику обязательных проверок.

## Requirements

### Requirement: Обязательные стадии конвейера Pull Request
Конвейер CI для событий `pull_request` в `main` и `push` в `main` MUST запускать независимые стадии `lint` (статический анализ, форматирование, границы импорта), `typecheck`, `test` (модульные и интеграционные тесты), `build` и `quality-gates`, а также агрегирующую проверку `ci-required`, которая завершается успешно только при зелёном статусе всех обязательных стадий.

#### Scenario: Полный успешный прогон PR
- **WHEN** открывается или обновляется Pull Request с корректными изменениями в коде и тестах
- **THEN** стадии `lint`, `typecheck`, `test`, `build` и `quality-gates` выполняются параллельно и завершаются с кодом `0`
- **AND** финальный статус `ci-required` завершается со статусом `success`

#### Scenario: Блокировка слияния при провале одной стадии
- **WHEN** в Pull Request присутствует ошибка типов, но `lint`, `test` и `build` проходят
- **THEN** стадия `typecheck` завершается со статусом `failure`
- **AND** агрегирующая проверка `ci-required` завершается со статусом `failure`, блокируя слияние PR

#### Scenario: Независимый сбор диагностики при падении
- **WHEN** стадия `lint` завершается с ошибкой
- **THEN** остальные независимые стадии (`typecheck`, `test`, `build`, `quality-gates`) продолжают выполнение без принудительной отмены, чтобы разработчик увидел все ошибки за один прогон

### Requirement: Отмена устаревших запусков и бюджет времени CI
Конвейер CI MUST настраивать группы конкурентности с отменой устаревших прогонов (`cancel-in-progress: true`) для веток Pull Request, никогда не отменять прогоны ветки `main`, и укладываться в бюджет времени ≤ `10` минут на холодном кэше и ≤ `4` минут на прогретом кэше для базовой фазы P00.

#### Scenario: Автоматическая отмена устаревшего прогона PR
- **WHEN** разработчик отправляет новый коммит в ветку открытого PR во время выполнения предыдущего CI-прогона этого PR
- **THEN** предыдущий запуск автоматически переводится в статус `cancelled`
- **AND** запускается новый прогон для последнего коммита

#### Scenario: Защита прогонов основной ветки от отмены
- **WHEN** в ветку `main` сливаются два PR подряд за короткий промежуток времени
- **THEN** предыдущий запуск CI на `main` не отменяется и завершается полностью

### Requirement: Кэширование зависимостей и задач оркестратора
Конвейер CI MUST кэшировать хранилище менеджера пакетов с ключом на основе ОС и хэша lockfile, а также кэш артефактов оркестратора задач с поддержкой опционального удалённого кэша через секреты репозитория и безопасным откатом к локальному кэшу CI (включая PR из форков без доступа к секретам).

#### Scenario: Восстановление кэша при неизменённом lockfile
- **WHEN** запускается CI на PR, не изменяющем lockfile
- **THEN** хранилище пакетов восстанавливается из кэша без повторного скачивания всех пакетов из сети
- **AND** не затронутые изменением пакеты получают кэш-хиты оркестратора задач

#### Scenario: Работа PR из внешнего форка без секретов удалённого кэша
- **WHEN** Pull Request открывается из внешнего форка, где секреты удалённого кэша недоступны
- **THEN** конвейер не завершается ошибкой аутентификации удалённого кэша, автоматически использует стандартный кэш GitHub Actions и завершает все проверки корректно

### Requirement: Инкрементальная фильтрация затронутых пакетов и полная проверка на main
На Pull Request конвейер CI MUST выполнять проверки только для затронутых diff пакетов и их зависимых (с автоматическим переключением на полный прогон монорепозитория при изменении корневых конфигов, lockfile или файлов `.github/workflows/**`); на `push` в `main` и плановых ночных прогонах MUST выполняться полный прогон всего монорепозитория.

#### Scenario: Точечная проверка при изменении одного листового приложения
- **WHEN** PR изменяет файлы только в `apps/admin`
- **THEN** инкрементальный фильтр запускает сборку и тесты только для `apps/admin` без пересборки `apps/game-server`

#### Scenario: Принудительный полный прогон при изменении корневого конфига
- **WHEN** PR изменяет `tsconfig.base.json`, lockfile или файл workflow в `.github/workflows/`
- **THEN** конвейер автоматически отключает сужение по diff и выполняет полный прогон всех 15 приложений и пакетов

#### Scenario: Полный прогон на ветке main
- **WHEN** коммит попадает в ветку `main` или срабатывает ночное расписание
- **THEN** конвейер запускает полную проверку всех пакетов и приложений независимо от состава последнего diff

### Requirement: Сервисные контейнеры для интеграционных тестов в CI
Стадия `test` в CI MUST поднимать эфемерные сервисные контейнеры PostgreSQL 17, Valkey 8 и NATS JetStream с теми же зафиксированными версиями образов, что и в локальном окружении, дожидаться их готовности по healthcheck, применять миграции и запускать интеграционные тесты без внешних сетевых зависимостей.

#### Scenario: Выполнение интеграционных тестов против сервисных контейнеров
- **WHEN** запускается стадия `test` в CI
- **THEN** сервисные контейнеры PostgreSQL 17, Valkey 8 и NATS JetStream переходят в состояние `healthy`
- **AND** миграции и интеграционные тесты `packages/db`, `apps/api` и `apps/game-server` проходят с кодом возврата `0`

#### Scenario: Согласованность версий образов локального стенда и CI
- **WHEN** выполняется проверка консистентности инфраструктуры
- **THEN** версии образов PostgreSQL, Valkey и NATS в workflow CI совпадают с зафиксированными версиями в `docker-compose.yml`

### Requirement: Публикация диагностических и сборочных артефактов
Конвейер CI MUST публиковать структурированные артефакты с ограниченным сроком хранения (`14` дней для PR, `30` дней для `main`): отчёты тестов (JUnit/JSON), отчёты покрытия кода (`lcov` и JSON summary), статистику размеров клиентских бандлов (`apps/client`, `apps/admin`) и логи провалов даже при неуспешном завершении шага.

#### Scenario: Публикация артефактов после успешного прогона
- **WHEN** стадии `test` и `build` завершаются успешно
- **THEN** в запуске CI доступны загруженные артефакты отчётов тестов, покрытия кода и размеров клиентских бандлов со сроком хранения `14` дней для PR (или `30` дней для `main`)

#### Scenario: Сохранение отчётов при провале тестов
- **WHEN** один из тестов в стадии `test` падает
- **THEN** артефакт JUnit-отчёта и диагностических логов всё равно загружается в запуск CI для разбора причины провала

### Requirement: Защита цепочки поставок CI и минимальные привилегии
Все сторонние действия (GitHub Actions) в файлах `.github/workflows/*.yml` MUST быть зафиксированы по полному 40-символьному commit SHA (запрещены плавающие теги вида `@v4` или `@main`), верхний уровень прав `GITHUB_TOKEN` MUST ограничиваться `contents: read` (с точечным повышением только для нужных джобов), а PR из форков MUST NOT получать права на запись или секреты.

#### Scenario: Валидация пиннинга SHA и прав токена в workflow
- **WHEN** выполняется проверка файлов `.github/workflows/*.yml` в стадии `quality-gates`
- **THEN** каждое внешнее `uses:` ссылается на 40-символьный hex SHA с комментарием версии
- **AND** каждый workflow явно задаёт `permissions: { contents: read }` на верхнем уровне

#### Scenario: Отклонение незафиксированного тега GitHub Action
- **WHEN** в файл workflow добавляется шаг `uses: actions/checkout@v4` вместо полного SHA
- **THEN** проверка безопасности workflow завершается с ненулевым кодом возврата и блокирует PR

### Requirement: Контракт обязательных проверок ветки main
Репозиторий MUST содержать версионируемое машиночитаемое описание правил защиты ветки `main` (ruleset), требующее прохождения статуса `ci-required`, актуальности ветки PR относительно `main`, минимум `1` одобрения ревью для слияния, запрет force-push и запрет удаления ветки `main`.

#### Scenario: Проверка наличия и валидности спецификации ruleset
- **WHEN** проверяется конфигурация защиты ветки в репозитории
- **THEN** файл ruleset проходит валидацию структуры и содержит обязательную проверку `ci-required`, запрет `force_push` и запрет `deletion` для `refs/heads/main`

#### Scenario: Обнаружение расхождения имени обязательной проверки
- **WHEN** имя финального агрегирующего job в workflow изменяется и перестаёт совпадать с именем в ruleset
- **THEN** проверка целостности CI завершается с ненулевым кодом возврата

### Requirement: Валидация спецификаций OpenSpec и синхронности конфигурации в CI
Конвейер CI MUST проверять синтаксис файлов workflow, актуальность шаблонов `.env.example` относительно схем конфигурации и строгую валидацию изменений OpenSpec, затронутых в текущем PR, отклоняя PR при любом нарушении контрактов.

#### Scenario: Валидация изменённого OpenSpec-артефакта в PR
- **WHEN** PR добавляет или изменяет файлы в `openspec/changes/<id>/`
- **THEN** CI автоматически запускает строгую валидацию этого изменения OpenSpec и завершает шаг с кодом `0` при отсутствии ошибок и предупреждений

#### Scenario: Дрейф шаблона переменных окружения относительно схемы
- **WHEN** в схему конфигурации добавляется новая обязательная переменная без добавления её в соответствующий `.env.example`
- **THEN** проверка синхронности конфигурации в CI завершается с ненулевым кодом возврата с перечислением недостающих ключей
