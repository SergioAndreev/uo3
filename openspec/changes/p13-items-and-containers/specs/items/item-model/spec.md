# Спецификация: items/item-model

## Purpose

Определяет каноническую модель предмета эпохи UO:Renaissance: уникальную идентификацию в пространстве серийных номеров, наследование статических флагов `TileData`, правила объединения в стаки, точный расчёт массы в десятых долях камня, износ, окраску, материализацию стартового инвентаря из шаблонов и формирование текстовых меток при одиночном клике.

## ADDED Requirements

### Requirement: Идентификация и базовые атрибуты предмета
Каждый экземпляр предмета SHALL иметь уникальный 32-битный серийный номер из диапазона `0x40000000..0x7FFFFFFF`, `templateId`, `graphicId` (`1..0x3FFF`), `hue` (`0..3000`), `amount` (`1..60000`), `weightTenths` (`>= 0`), битовую маску состояния и ровно одну локацию владения (`World`, `Container` или `MobileLayer`). Попытка создать предмет вне диапазона серийников MUST отклоняться с `ERR_ITEM_INVALID_SERIAL`.

#### Scenario: Создание валидного экземпляра предмета из шаблона
- **WHEN** сервер создаёт предмет по шаблону с `graphicId = 0x0EED` (золотые монеты) и выделенным серийником `0x40000105`
- **AND** предмет помещается в локацию `Container` с серийником родителя `0x40000100`
- **THEN** предмет получает уникальный серийный номер `0x40000105`, `amount = 1`, `hue = 0` и ссылку ровно на один родительский контейнер

#### Scenario: Отказ при серийном номере из диапазона мобилей
- **WHEN** подсистема создания предметов получает запрос с серийным номером `0x00000050` или `0x20000010`
- **THEN** операция отклоняется с кодом ошибки `ERR_ITEM_INVALID_SERIAL`
- **AND** экземпляр предмета не добавляется в индекс мира

### Requirement: Наследование флагов TileData и переопределение свойств
Предмет SHALL наследовать базовые 64-битные флаги (`Stackable`, `Container`, `Wearable`, `Impassable`, `Surface`, `LightSource`, `Door`), базовый вес и слой из записи `TileData` по своему `graphicId`. Шаблон предмета MAY переопределять вес, слой и динамические флаги (`Movable`, `Newbie`/`Blessed`, `LockedDown`), но MUST NOT объявлять одновременно флаги `Stackable` и `Container`.

#### Scenario: Наследование флагов из TileData по умолчанию
- **WHEN** создаётся предмет без явных переопределений в шаблоне с `graphicId`, у которого в `TileData` установлены флаги `Wearable` и `LightSource`
- **THEN** экземпляр предмета автоматически получает флаги `Wearable` и `LightSource` и канонический слой из записи `TileData`

#### Scenario: Запрет совмещения флагов Stackable и Container
- **WHEN** валидатор каталога или сервер проверяет шаблон предмета, в котором одновременно включены `Stackable = true` и `Container = true`
- **THEN** валидация завершается ошибкой `ERR_ITEM_INVALID_TEMPLATE_FLAGS`

### Requirement: Складывание предметов в стаки
Предметы SHALL объединяться в один стак до максимального количества `MAX_STACK_AMOUNT = 60000` только если оба экземпляра имеют флаг `Stackable`, одинаковые `templateId`, `graphicId`, `hue` и идентичные динамические флаги (`Newbie`), а также не имеют индивидуального состояния износа. Если сумма превышает `60000`, целевой стак MUST заполняться до `60000`, а остаток сохраняться в исходном предмете.

#### Scenario: Полное слияние двух однородных стаков
- **WHEN** стак из `250` золотых монет (`graphicId = 0x0EED`, `hue = 0`) объединяется со стаком из `400` таких же золотых монет
- **THEN** целевой стак получает `amount = 650`, а исходный экземпляр предмета уничтожается

#### Scenario: Частичное слияние при достижении лимита 60000
- **WHEN** стак из `25000` стрел объединяется с целевым стаком из `50000` идентичных стрел
- **THEN** целевой стак устанавливается в `amount = 60000`
- **AND** исходный предмет сохраняется с остатком `amount = 15000`

#### Scenario: Отказ слияния предметов с разным Hue или флагом Newbie
- **WHEN** предмет с `Stackable = true` и `hue = 1153` объединяется с предметом того же `templateId`, но `hue = 0`
- **THEN** слияние отклоняется с кодом `ERR_ITEM_NOT_STACKABLE_TOGETHER`, и оба предмета остаются раздельными экземплярами

### Requirement: Расчёт массы предмета и стака
Удельный вес предмета SHALL храниться в десятых долях камня (`unitWeightTenths`, целое число `>= 0`, где `10` единиц равны `1.0` камня). Полный вес стака из `amount` единиц в камнях MUST вычисляться детерминированно по формуле `totalStones = ceil((unitWeightTenths * amount) / 10)`. Предметы с `unitWeightTenths = 0` MUST иметь вес `0` камней при любом `amount`.

#### Scenario: Расчёт веса стака золотых монет
- **WHEN** стак золотых монет имеет удельный вес `unitWeightTenths = 0` или дробный вес `0.02` камня по правилу шаблона (`2` камня на `100` монет)
- **AND** количество монет в стаке составляет `550` при удельном весе `1` десятая камня на `5` монет
- **THEN** итоговый вес стака вычисляется детерминированно без потери точности с округлением вверх до целого числа камней

#### Scenario: Расчёт веса стака реагентов с удельным весом 0.1 камня
- **WHEN** стак реагентов имеет `unitWeightTenths = 1` (`0.1` камня) и `amount = 14`
- **THEN** вес стака в десятых долях составляет `14`, а округлённый вес для проверки перегруза равен `ceil(14 / 10) = 2` камня

### Requirement: Формирование текстовой метки при одиночном клике
При намерении одиночного клика (`SingleClickIntent`) по предмету в пределах AOI (или в открытом контейнере) сервер SHALL возвращать текстовую метку (`SingleClickLabelEvent`). Метка MUST включать количество для `amount > 1` (формат `"<amount> <pluralName>"`), префикс `"a "`/`"an "` для `amount = 1`, суффикс `"[blessed]"` для предметов с флагом `Newbie`, а для контейнеров — число предметов и их вес в камнях.

#### Scenario: Одиночный клик по стаку предметов
- **WHEN** клиент отправляет `SingleClickIntent` для стака из `120` бинтов (`bandages`) в радиусе AOI
- **THEN** сервер отвечает событием `SingleClickLabelEvent` с текстом `"120 bandages"`

#### Scenario: Одиночный клик по стартовому кинжалу с флагом Newbie
- **WHEN** клиент отправляет `SingleClickIntent` для одиночного предмета `"dagger"` с `amount = 1` и установленным флагом `Newbie`
- **THEN** сервер возвращает метку `"a dagger [blessed]"`

#### Scenario: Одиночный клик по открытому или доступному рюкзаку
- **WHEN** клиент отправляет `SingleClickIntent` по рюкзаку, содержащему `12` предметов суммарным весом `34` камня
- **THEN** сервер возвращает метку `"a backpack (12 items, 34 stones)"`

### Requirement: Износостойкость и целостность предметов
Экипируемые предметы оружия, брони и щитов SHALL поддерживать целочисленные атрибуты `durabilityCurrent` и `durabilityMax` (`0..255`). При снижении `durabilityCurrent` до `0` предмет с `durabilityMax > 0` MUST немедленно разрушаться с уведомлением владельца. Предметы с `durabilityMax = 0` (одежда, украшения, магические жезлы без износа) MUST считаться неразрушаемыми от износа.

#### Scenario: Разрушение предмета при падении прочности до нуля
- **WHEN** у надетого щита с `durabilityCurrent = 1` и `durabilityMax = 45` прочность уменьшается на `1`
- **THEN** `durabilityCurrent` становится `0`, предмет атомарно удаляется со слоя экипировки, а владельцу отправляется системное сообщение о поломке

#### Scenario: Неразрушаемость предмета с нулевой максимальной прочностью
- **WHEN** предмет одежды создан с `durabilityMax = 0` и `durabilityCurrent = 0`
- **THEN** проверка износа игнорирует данный предмет и не разрушает его

### Requirement: Каталог шаблонов предметов и стартовая выдача
Все шаблоны предметов SHALL загружаться из `@uo3/content` и проходить строгую валидацию JSON Schema при старте сервера. При первом входе нового персонажа в мир сервер MUST идемпотентно материализовать его `StarterLoadoutV1` в рамках критической транзакции RPO=0: создать `Backpack` (`layer = 0x15`), `BankBox` (`layer = 0x1D`), стартовую экипировку и предметы с флагом `Newbie`.

#### Scenario: Первичная материализация StarterLoadoutV1 при входе в мир
- **WHEN** персонаж с `starterLoadoutMaterialized = false` впервые входит в комнату партиции
- **THEN** сервер в одной критической транзакции создаёт системные контейнеры `Backpack` и `BankBox`, надевает стартовую одежду, кладёт стартовые предметы в рюкзак и устанавливает флаг материализации в `true`

#### Scenario: Идемпотентность при повторном входе персонажа
- **WHEN** персонаж с уже установленным флагом `starterLoadoutMaterialized = true` повторно подключается к серверу
- **THEN** повторная выдача стартовых предметов не выполняется, а загружаются существующие предметы из хранилища

### Requirement: Окраска предмета и валидация палитры Hue
Атрибут цвета `hue` предмета SHALL принимать значения в диапазоне `0..3000` (`0` — оригинальные цвета спрайта, `1..3000` — индекс палитры `hues`). Попытка присвоить `hue > 3000` при создании или модификации предмета MUST отклоняться с ошибкой `ERR_ITEM_INVALID_HUE` либо нормализоваться маской `0x0FFF` с проверкой верхней границы `3000`.

#### Scenario: Создание окрашенной ткани с валидным Hue
- **WHEN** создаётся предмет ткани с `hue = 1157`
- **THEN** предмет сохраняет `hue = 1157` и реплицирует его клиентам в AOI для применения палитры

#### Scenario: Отклонение некорректного индекса Hue
- **WHEN** запрос создания или изменения предмета передаёт `hue = 3500`
- **THEN** операция отклоняется с кодом ошибки `ERR_ITEM_INVALID_HUE`
