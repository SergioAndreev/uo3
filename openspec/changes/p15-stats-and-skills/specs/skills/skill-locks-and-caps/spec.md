# Спецификация: skills/skill-locks-and-caps

## Purpose

Данная спецификация определяет управление состояниями блокировки навыков и характеристик (`UP`, `DOWN`, `LOCKED`), соблюдение индивидуального потолка навыка `100.0` (`1000` десятых) и суммарного капа всех 49 навыков `700.0` (`7000` десятых), алгоритм детерминированного вытеснения навыков в статусе `DOWN`, персистентность в PostgreSQL и аудит административных изменений.

## ADDED Requirements

### Requirement: Состояния блокировки каждого навыка UP DOWN LOCKED
Каждый из 49 навыков персонажа SHALL иметь независимое состояние блокировки (`0 = UP`, `1 = DOWN`, `2 = LOCKED`), равное `UP` по умолчанию при создании персонажа; навык в состоянии `DOWN` или `LOCKED` MUST NOT увеличивать свой `BaseValue` ни при каких проверках навыков.

#### Scenario: Подавление прироста для навыка в статусе LOCKED или DOWN
- **WHEN** персонаж успешно выполняет сложное действие навыком `Evaluating Intelligence`, у которого установлен статус `LOCKED` или `DOWN`
- **AND** сервер выполняет фазу расчёта прироста
- **THEN** бросок прироста для этого навыка пропускается, `BaseValue` не изменяется, однако проверка побочного роста статов (`STR`/`DEX`/`INT`) выполняется штатно

#### Scenario: Начальная установка статуса UP для всех 49 навыков нового персонажа
- **WHEN** создаётся новый персонаж и инициализируется его таблица из 49 навыков
- **AND** сервер загружает состояние блокировок
- **THEN** все 49 навыков имеют статус блокировки `UP` (`0`)

### Requirement: Клиентские намерения переключения блокировок навыков и статов
Сервер SHALL обрабатывать клиентские намерения смены блокировки навыка (`SkillId 0..48`, `lockState 0..2`) и характеристики (`StatType 0..2`, `lockState 0..2`) с лимитом `20` запросов в секунду на сессию, отклоняя невалидные параметры кодами `ERR_INVALID_LOCK_TARGET`, `ERR_INVALID_LOCK_STATE` или `ERR_RATE_LIMITED`.

#### Scenario: Успешное переключение статуса блокировки навыка клиентом
- **WHEN** клиент отправляет намерение `SetSkillLockIntent` с `skillId = 40` (`Swordsmanship`) и `lockState = 2` (`LOCKED`)
- **AND** лимит частоты запросов не превышен
- **THEN** сервер обновляет статус блокировки навыка `40` на `LOCKED`, помечает состояние для сохранения и отправляет подтверждающий пакет `SkillLockUpdated`

#### Scenario: Отклонение невалидного статуса блокировки или превышения rate-limit
- **WHEN** клиент отправляет намерение с `lockState = 5` либо отправляет `25` запросов смены блокировки за `500` мс
- **AND** сервер валидирует входящий пакет
- **THEN** запрос с `lockState = 5` отклоняется кодом `ERR_INVALID_LOCK_STATE`, а запросы сверх лимита `20/с` отклоняются кодом `ERR_RATE_LIMITED`

### Requirement: Инвариант индивидуального потолка навыка 100.0
Базовое значение `BaseValue` любого из 49 навыков SHALL всегда находиться в диапазоне `0..1000` (`0.0..100.0`); когда `BaseValue` достигает `1000`, дальнейший прирост этого навыка MUST прекращаться независимо от статуса блокировки `UP`.

#### Scenario: Прекращение прироста навыка при достижении уровня Grandmaster 100.0
- **WHEN** навык персонажа имеет `BaseValue = 1000` и статус блокировки `UP`
- **AND** персонаж выполняет действие этим навыком
- **THEN** сервер не выполняет бросок прироста для данного навыка и `BaseValue` остаётся равным `1000`

#### Scenario: Зажатие шага ускоренного старта границей индивидуального капа
- **WHEN** навык имеет индивидуальный лимит `1000` (или порог ускоренного старта `100` при `BaseValue = 98`) и выпадает прирост `+4` десятых
- **AND** сервер применяет изменение `BaseValue`
- **THEN** значение корректно зажимается пороговым лимитом и никогда не превышает `1000`

### Requirement: Инвариант суммарного капа навыков 700.0
Сумма базовых значений всех 49 навыков персонажа `TotalSkillTenths = sum(BaseValue[0..48])` MUST NOT превышать `7000` (`700.0` очков) ни в памяти игрового сервера, ни в транзакциях PostgreSQL; временные бонусы (`TempSkillBonusTenths`) НЕ учитываются в `TotalSkillTenths`.

#### Scenario: Свободный прирост навыка до достижения суммарного капа 7000
- **WHEN** у персонажа `TotalSkillTenths = 6995` и навык в статусе `UP` получает прирост `+1` десятую долю
- **AND** сервер применяет прирост
- **THEN** `TotalSkillTenths` становится `6996` без уменьшения каких-либо других навыков

#### Scenario: Невлияние временных бонусов экипировки на суммарный кап 7000
- **WHEN** у персонажа `TotalSkillTenths = 6990` и надето кольцо с бонусом `+100` десятых (`+10.0`) к навыку
- **AND** персонаж получает прирост `+1` десятую долю к базовому навыку
- **THEN** прирост разрешается, так как `TotalSkillTenths` увеличивается с `6990` до `6991` (`<= 7000`)

### Requirement: Детерминированное вытеснение навыков в статусе DOWN при достижении капа
Когда навык в статусе `UP` должен вырасти на `delta` десятых (`1..5`), но `TotalSkillTenths + delta > 7000`, сервер SHALL атомарно списать `overflow = (TotalSkillTenths + delta) - 7000` десятых с других навыков в статусе `DOWN` (`BaseValue > 0`) в порядке возрастания их `SkillId`.

#### Scenario: Вытеснение одного навыка-донора в статусе DOWN на капе 700.0
- **WHEN** у персонажа `TotalSkillTenths = 7000`, навык `SkillId = 25` (`Magery`, `UP`, `BaseValue = 900`) получает `+1` десятую, а навык `SkillId = 5` (`Camping`, `DOWN`, `BaseValue = 150`) доступен для снижения
- **AND** сервер применяет атомарный переход состояния
- **THEN** `Magery` становится `901`, `Camping` уменьшается до `149`, клиенту отправляются дельты обоих навыков, а `TotalSkillTenths` остаётся равным `7000`

#### Scenario: Распределение списания между несколькими навыками DOWN при недостатке очков у первого донора
- **WHEN** у персонажа `TotalSkillTenths = 6999`, навык на ускоренном старте (`BaseValue = 50`, `UP`) получает прирост `delta = 3` (`overflow = 2`), при этом `SkillId = 2` (`DOWN`) имеет `BaseValue = 1`, а `SkillId = 10` (`DOWN`) имеет `BaseValue = 50`
- **AND** сервер выполняет вытеснение в порядке возрастания `SkillId`
- **THEN** `SkillId = 2` уменьшается с `1` до `0`, `SkillId = 10` уменьшается с `50` до `49`, растущий навык увеличивается с `50` до `53`, а `TotalSkillTenths` равен `7000`

### Requirement: Блокировка прироста при отсутствии доступного резерва вытеснения
Если для прироста на `delta` десятых требуется вытеснить `overflow > 0` десятых, но суммарный `BaseValue` всех остальных навыков в статусе `DOWN` меньше `overflow`, сервер SHALL полностью отменить прирост без частичного списания доноров и отправить клиенту троттлируемое уведомление `ERR_SKILL_CAP_REACHED`.

#### Scenario: Полный отказ в приросте на капе 7000 при отсутствии навыков в статусе DOWN
- **WHEN** у персонажа `TotalSkillTenths = 7000` и все 49 навыков находятся в статусах `UP` или `LOCKED` (либо навыки в `DOWN` имеют `BaseValue == 0`)
- **AND** срабатывает условие прироста для навыка в статусе `UP`
- **THEN** ни один навык не изменяет своё значение, а клиенту отправляется код `ERR_SKILL_CAP_REACHED` (не чаще одного раза в `10000` мс)

### Requirement: Персистентность блокировок и значений навыков в PostgreSQL
Сервер SHALL сохранять обновлённые `BaseValue` и `lockState` навыков, а также базовые характеристики и их блокировки в PostgreSQL в рамках 60-секундного цикла dirty-flush и синхронно при выходе персонажа, передаче между партициями (handoff) или завершении работы комнаты.

#### Scenario: Сохранность значений и блокировок после перезахода персонажа
- **WHEN** персонаж в игровой сессии получает `+1` десятую к навыку `SkillId = 17` (`Healing`), меняет его блокировку на `LOCKED`, а блокировку `DEX` на `DOWN`, после чего выходит из игры
- **AND** персонаж повторно входит в игровой мир
- **THEN** из PostgreSQL загружаются точные сохранённые значения `BaseValue`, `skillLock = LOCKED` и `dexLock = DOWN` без потерь

#### Scenario: Защита целостности капа 7000 и диапазонов на уровне ограничений БД
- **WHEN** батчевый flush записывает массив из 49 навыков персонажа в таблицу `character_skills`
- **AND** транзакция фиксируется в PostgreSQL
- **THEN** ограничения БД гарантируют `0 <= value_tenths <= 1000`, `lock_state IN (0, 1, 2)` и соблюдение суммарного инварианта персонажа

### Requirement: Аудит и административная коррекция статов и навыков
Административные команды (`AccessLevel >= GameMaster`) изменения базовых статов или навыков SHALL валидировать индивидуальные границы (`10..100` для статов, `0..1000` для навыков) и суммарные капы (`225` / `7000`, если не указан явный флаг `allowCapOverride = true` для `AccessLevel >= Seer`), обязательно записывая неизменяемую запись в журнал аудита.

#### Scenario: Изменение навыка персонажа командой GameMaster с записью в аудит
- **WHEN** сотрудник с `AccessLevel = GameMaster` выполняет команду установки навыка `Magery = 850` персонажу игрока с текущим `TotalSkillTenths = 5200` и указывает причину `"Restore after bug"`
- **AND** новая сумма навыков не превышает `7000`
- **THEN** `BaseValue` навыка устанавливается в `850`, клиенту игрока отправляется `SkillUpdated`, а в таблицу аудита записываются `actorAccountId`, `targetCharacterId`, `field = "skill:25"`, старое и новое значения и причина

#### Scenario: Отказ в превышении капа 7000 без привилегии и явного флага override
- **WHEN** сотрудник с `AccessLevel = GameMaster` пытается установить персонажу с `TotalSkillTenths = 6800` новый навык с `0` до `500` (итого `7300`) без прав `Seer` и флага `allowCapOverride`
- **AND** сервер проверяет инвариант капа
- **THEN** команда отклоняется с кодом `ERR_CAP_EXCEEDED`, значения навыков персонажа не меняются
