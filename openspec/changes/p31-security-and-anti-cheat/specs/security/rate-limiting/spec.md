# Спецификация: security/rate-limiting

## Purpose

Спецификация регламентирует многоуровневую защиту игрового сервера реального времени и REST API от сетевого флуда, злоупотребления очередями намерений, ресурсоёмких запросов и перегрузки соединений. Ограничения сохраняют стабильность 20-герцового тика (50 мс) и изолируют шумных клиентов без ущерба для остальных игроков.

## ADDED Requirements

### Requirement: Per-Connection WebSocket Token Bucket

На каждое активное WebSocket-соединение SHALL действовать общий ограничитель интенсивности: не более `60` входящих кадров в секунду (всплеск до `120` кадров) и не более `65536` байт/с; превышение отбрасывается с кодом `ERR_RATE_LIMITED`, а `3` переполнения в течение `10` с закрывают соединение с кодом `4108`.

#### Scenario: Поглощение кратковременного всплеска до 120 кадров
- **WHEN** клиент при открытии окна рюкзака и макросе экипировки отправляет `90` валидных кадров за `1` с, а затем снижает поток до `20` кадров/с
- **THEN** всплеск пропускается без ошибок за счёт ёмкости `120` кадров
- **AND** соединение остаётся стабильным.

#### Scenario: Отбрасывание трафика при превышении лимита байт или кадров
- **WHEN** клиент отправляет поток из `200` кадров/с или `100` Кбайт/с непрерывно
- **THEN** избыточные кадры отбрасываются до декодирования тела с уведомлением `ERR_RATE_LIMITED`
- **AND** сервер не тратит время тика на обработку отброшенных пакетов.

#### Scenario: Разрыв соединения при систематическом флуде кадрами
- **WHEN** клиент трижды переполняет общий token bucket в течение `10` с
- **THEN** сервер закрывает WebSocket-соединение с кодом `4108`
- **AND** освобождает ресурсы сессии в комнате.

### Requirement: Per-Intent Action Rate Quotas

Помимо общего лимита MUST действовать раздельные квоты по классам игровых намерений: шаги ≤ `12`/с, использование навыков и выбор цели ≤ `5`/с, операции Drag&Drop ≤ `4`/с, нажатия кнопок гампов ≤ `5`/с, запросы торговли и вендоров ≤ `2`/с; превышение возвращает `ERR_ACTION_RATE_LIMITED`.

#### Scenario: Ограничение спама таргетами и использованием навыков
- **WHEN** клиент отправляет `15` запросов выбора цели или применения навыка в течение `1` с
- **THEN** первые `5` запросов в пределах квоты обрабатываются
- **AND** остальные отклоняются с кодом `ERR_ACTION_RATE_LIMITED` без блокировки ходьбы.

#### Scenario: Раздельность корзин между ходьбой и торговлей
- **WHEN** клиент исчерпал лимит нажатий кнопок вендора (`2`/с)
- **THEN** новые запросы покупки отклоняются с `ERR_ACTION_RATE_LIMITED`
- **AND** клиент по-прежнему может отправлять намерения шага в пределах своей квоты `12`/с.

#### Scenario: Защита очереди Drag&Drop от автоматизированного спама
- **WHEN** клиент отправляет более `4` операций захвата и сброса предметов в секунду
- **THEN** сервер отклоняет избыточные попытки с `ERR_ACTION_RATE_LIMITED`
- **AND** уже захваченный предмет остаётся в консистентном состоянии.

### Requirement: Speech and Chat Flood Escalation

Локальная речь (радиус `1`/`15`/`18` тайлов), пати-чат и гильд-чат SHALL ограничиваться квотой не более `2` сообщений в секунду с всплеском `5` сообщений за `5` с и запретом более `3` идентичных строк подряд; нарушение накладывает автоматический мут канала на `30` с с кодом `ERR_SPEECH_FLOOD`.

#### Scenario: Автоматический мут за серию быстрых реплик
- **WHEN** игрок отправляет `6` сообщений в общий чат в течение `4` с
- **THEN** 6-е сообщение отклоняется с ошибкой `ERR_SPEECH_FLOOD`
- **AND** публикация в чат блокируется на `30` с с уведомлением о времени снятия.

#### Scenario: Подавление повторяющегося спама (copy-paste flood)
- **WHEN** игрок отправляет `4` идентичные рекламные фразы подряд с интервалом `3` с
- **THEN** четвёртое сообщение отклоняется с `ERR_SPEECH_FLOOD`
- **AND** остальные игроки в радиусе `18` тайлов не получают спам-дубликат.

#### Scenario: Эскалация длительности мута при повторном флуде
- **WHEN** в течение `600` с после снятия `30`-секундного мута игрок повторно нарушает лимит чата
- **THEN** длительность мута увеличивается до `300` с
- **AND** инцидент фиксируется в журнале модерации.

### Requirement: REST API Endpoint Rate Limiting

Все маршруты `/api/v1/*` MUST защищаться скользящими лимитами по IP и по аккаунту: вход/MFA/OAuth — до `5` req/мин на IP и `10` req/`15` мин на аккаунт; выдача игровых билетов — до `10` req/мин на аккаунт; чтение профилей и каталогов — до `60` req/мин на IP, возвращая HTTP `429` с заголовком `Retry-After`.

#### Scenario: Ограничение перебора пароля и кодов MFA
- **WHEN** с одного IP поступает `6`-й запрос на вход или проверку MFA за `60` с
- **THEN** API немедленно возвращает статус `429` и заголовок `Retry-After`
- **AND** не выполняет дорогостоящую криптографическую проверку пароля.

#### Scenario: Ограничение частоты запросов игровых билетов
- **WHEN** авторизованный аккаунт запрашивает создание игрового билета `11` раз за `1` минуту
- **THEN** 11-й запрос отклоняется со статусом `429` и ошибкой `ERR_RATE_LIMITED`
- **AND** действующие активные игровые сессии аккаунта не разрываются.

#### Scenario: Заголовок ожидания при превышении лимита чтения профилей
- **WHEN** клиент превышает `60` запросов в минуту к публичным и профильным GET-эндпоинтам
- **THEN** сервер возвращает HTTP `429` с точным числом секунд в заголовке `Retry-After`
- **AND** восстанавливает доступ после истечения окна.

### Requirement: Pre-Auth Connection and Handshake Flood Guard

Шлюз WebSocket SHALL ограничивать каждый IP-адрес максимум `8` одновременными подключениями и `20` попытками handshake за `60` с; любое соединение, не завершившее авторизацию валидным билетом в течение `5000` мс, принудительно закрывается.

#### Scenario: Сброс «висящего» неавторизованного сокета (Slowloris)
- **WHEN** клиент открывает WebSocket-соединение и не присылает валидный игровой билет в течение `5000` мс
- **THEN** сервер закрывает сокет по таймауту авторизации до выделения сущности игрока
- **AND** освобождает слот подключения для данного IP.

#### Scenario: Блокировка превышения лимита параллельных сокетов с одного IP
- **WHEN** с одного IP-адреса открывается 9-е одновременное WebSocket-соединение
- **THEN** новое рукопожатие отклоняется с отказом подключения (`429` / WS `4108`)
- **AND** первые `8` авторизованных соединений продолжают работать без перебоев.

#### Scenario: Ограничение частоты переподключений (reconnect storm)
- **WHEN** клиент генерирует более `20` handshake-попыток за `60` с с одного IP
- **THEN** последующие рукопожатия отклоняются до истечения окна
- **AND** событие всплеска регистрируется в метриках защиты.

### Requirement: Expensive Operation and Tick CPU Budget Isolation

Ресурсоёмкие запросы по инициативе клиента (поиск пути, поиск товаров и домов, выборки истории) SHALL иметь квоту не более `2` операций/с и лимит времени `4` мс на игрока в рамках одного тика `50` мс; при превышении запрос отменяется с `ERR_COMPUTE_BUDGET_EXCEEDED`.

#### Scenario: Защита тика 20 Гц от тяжёлого запроса поиска пути
- **WHEN** клиент запрашивает сложный маршрут или серию из `5` запросов поиска пути за секунду
- **THEN** сервер ограничивает выполнение двумя запросами в секунду и прерывает вычисление при превышении `4` мс
- **AND** остальные игроки комнаты не испытывают просадки частоты тика ниже `20` Гц.

#### Scenario: Изоляция нагрузочного запроса поиска по вендорам
- **WHEN** игрок отправляет частые запросы фильтрации списка домов или вендоров
- **THEN** API или игровой сервер применяет квоту `2` req/с и кэшированные индексы
- **AND** отклоняет избыточные запросы с кодом `ERR_COMPUTE_BUDGET_EXCEEDED`.

#### Scenario: Честное распределение бюджета при одновременных запросах
- **WHEN** 20 игроков одновременно выполняют допустимые действия в одном тике
- **THEN** квота на одного клиента гарантирует равномерный доступ без захвата тика одним участником
- **AND** ни один клиент не может монополизировать цикл симуляции.

### Requirement: Outbound Queue Bounding and Slow-Client Eviction

Исходящая очередь обновлений на одно соединение MUST ограничиваться `256` Кбайт и `200` сообщениями; при заполнении выше `75%` сервер сбрасывает второстепенные косметические события, а при простое чтения или переполнении дольше `5000` мс отключает клиента без блокировки комнаты.

#### Scenario: Деградация некритичных событий при перегруженном канале клиента
- **WHEN** исходящий буфер медленного клиента достигает `150` сообщений или `192` Кбайт
- **THEN** сервер отбрасывает второстепенные косметические эффекты и звуки, сохраняя критические обновления позиций, урона и торговли
- **AND** не приостанавливает отправку патчей другим игрокам комнаты.

#### Scenario: Отключение полностью зависшего потребителя
- **WHEN** клиент не вычитывает сокет и буфер остаётся переполненным свыше `5000` мс
- **THEN** сервер принудительно разрывает соединение и запускает стандартный таймаут логаута персонажа
- **AND** освобождает буферную память.

#### Scenario: Сохранение критических уведомлений транзакций при умеренной очереди
- **WHEN** очередь клиента загружена на `50%`, но проходит подтверждение сделки или закрытие диалога
- **THEN** критическое уведомление доставляется без отбрасывания
- **AND** состояние клиента остаётся согласованным с сервером.

### Requirement: Distributed Limit Consistency and Fail-Closed Policy

Счётчики лимитов API и межшардовых действий SHALL храниться централизованно для консистентности между экземплярами сервиса; при кратковременной недоступности общего хранилища критические маршруты входа и транзакций переходят в безопасный отказ или локальный строгий лимит на `5` с.

#### Scenario: Согласованный лимит входа через разные реплики API
- **WHEN** злоумышленник распределяет `6` запросов входа между двумя разными репликами API в течение `60` с
- **THEN** распределённый счётчик блокирует 6-й запрос с кодом HTTP `429`
- **AND** не позволяет умножить квоту на количество реплик.

#### Scenario: Поведение критических маршрутов при сбое хранилища лимитов
- **WHEN** общее хранилище лимитов недоступно более `5` с
- **THEN** публичные эндпоинты аутентификации и смены прав включают строгий локальный аварийный лимит `2` req/мин на IP вместо отключения защиты
- **AND** в мониторинг отправляется критический алерт.

#### Scenario: Применение явных политик для внутренних и тестовых сервисов
- **WHEN** внутренний доверенный сервис или нагрузочный профиль dev-среды обращается с авторизованным сервисным ключом
- **THEN** применяются конфигурируемые лимиты из профиля среды без ослабления правил продакшена
- **AND** все исключения явно протоколируются.

### Requirement: Abuse Telemetry and Automated IP Cooldown

Каждое срабатывание лимитов MUST порождать структурированную телеметрию с указанием опкода или маршрута и маскированного источника; при `200` и более отклонённых запросов за `60` с от одного источника или аккаунта накладывается автоматический cooldown на `600` с.

#### Scenario: Автоматическая временная блокировка агрессивного флудера
- **WHEN** один IP-адрес или аккаунт генерирует `200` отклонённых по лимиту запросов за `60` с
- **THEN** система помещает источник в автоматический cooldown на `600` с
- **AND** все дальнейшие запросы немедленно отклоняются на граничном уровне с минимальной нагрузкой.

#### Scenario: Отсутствие утечки секретов в метриках флуда
- **WHEN** фиксируется событие превышения лимита на маршруте входа или WebSocket
- **THEN** в метрике и логе сохраняются код ответа, счётчик и хэш-маска источника
- **AND** токены, пароли и тела сообщений в телеметрию не попадают.

#### Scenario: Снятие cooldown по истечении срока
- **WHEN** истекают `600` с временной блокировки без повторных аномалий
- **THEN** источник автоматически восстанавливает стандартные квоты
- **AND** запись о блокировке остаётся в журнале инцидентов.
