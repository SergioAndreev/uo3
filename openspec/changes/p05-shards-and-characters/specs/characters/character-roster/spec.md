# Спецификация: characters/character-roster

## Purpose

Определяет управление списком персонажей аккаунта в рамках конкретного шарда: учёт квот и индексов слотов, анти-флуд ограничения создания, отложенное удаление с грейс-периодом и возможностью отмены, контролируемое переименование с историей имён, изоляцию данных между аккаунтами и административные операции персонала.

## ADDED Requirements

### Requirement: Просмотр списка персонажей аккаунта на шарде
Система SHALL предоставлять эндпоинт `GET /api/v1/shards/:shardId/characters`, возвращающий не удалённых персонажей аутентифицированного аккаунта на шарде по возрастанию `slotIndex`. Карточка MUST включать `id`, `serial`, `slotIndex`, `name`, `status`, внешность, сводку экипировки, статы, топ-3 навыка, фасет, регион, `lastPlayedAt`, таймер удаления и квоту слотов.

#### Scenario: Получение ростера с несколькими персонажами
- **WHEN** аутентифицированный игрок с двумя персонажами на слотах 0 и 2 запрашивает `GET /api/v1/shards/britannia-eu/characters`
- **THEN** система возвращает HTTP `200` с массивом из двух карточек в порядке `[slotIndex: 0, slotIndex: 2]` и сводкой `{ usedSlots: 2, maxSlots: 5, canCreateNew: true }`

#### Scenario: Пустой ростер на новом шарде
- **WHEN** игрок впервые открывает шард без созданных персонажей
- **THEN** система возвращает HTTP `200` с пустым массивом `characters: []` и `{ usedSlots: 0, maxSlots: 5, canCreateNew: true }`

#### Scenario: Исключение окончательно удалённых персонажей из ростера игрока
- **WHEN** один из персонажей аккаунта перешёл в статус `deleted` после окончания грейс-периода
- **THEN** он не возвращается в ответе `GET /api/v1/shards/:shardId/characters` и не учитывается в `usedSlots`

### Requirement: Квоты слотов персонажей по правилам шарда и аккаунта
Каждый шард MUST ограничивать число слотов на аккаунт параметром `maxCharactersPerAccount` (по умолчанию 5 для UO:R, 1 для `siege_perilous`, допустимый диапазон 1–7), с возможностью индивидуального расширения для аккаунта до жёсткого потолка 7. Все персонажи в статусах `active`, `rename_required`, `staff_locked` и `pending_deletion` MUST занимать уникальный `slotIndex` из диапазона `0..(maxSlots - 1)`.

#### Scenario: Отказ создания при заполнении всех слотов шарда
- **WHEN** аккаунт имеет 5 не удалённых персонажей (включая одного в статусе `pending_deletion`) на шарде с лимитом 5 и пытается создать шестого
- **THEN** система отклоняет запрос с HTTP `409` и кодом `CHARACTER_SLOT_LIMIT_REACHED`

#### Scenario: Однослотовое ограничение шарда Siege Perilous
- **WHEN** аккаунт уже имеет 1 персонажа на шарде типа `siege_perilous` и запрашивает ростер или создание второго персонажа
- **THEN** ростер возвращает `canCreateNew: false` с причиной `CHARACTER_SLOT_LIMIT_REACHED`, а попытка создания отклоняется с HTTP `409`

#### Scenario: Учёт дополнительных слотов аккаунта в пределах потолка 7
- **WHEN** аккаунту начислено +2 дополнительных слота на стандартном UO:R шарде (базовый лимит 5)
- **THEN** система разрешает до 7 персонажей, а при попытке начислить слоты сверх 7 ограничивает максимум значением 7

### Requirement: Анти-флуд ограничения частоты создания персонажей
Для защиты от сквоттинга имён и массового создания персонажей ради стартовых наборов система MUST ограничивать число созданий персонажей одним аккаунтом на одном шарде до `maxCreationsPer24h` (по умолчанию 5 за скользящие 24 часа, настраивается на шарде). Ограничение не распространяется на `AccessLevel >= Administrator`.

#### Scenario: Превышение суточного лимита создания персонажей
- **WHEN** игрок создал 5 персонажей за последние 24 часа (даже если часть из них была удалена) и пытается создать шестого
- **THEN** система отклоняет запрос с HTTP `429`, кодом `CHARACTER_CREATION_RATE_LIMITED` и заголовком `Retry-After`

#### Scenario: Обход анти-флуд лимита для администратора
- **WHEN** администратор создаёт 6-го тестового персонажа за сутки на тестовом шарде
- **THEN** запрос выполняется успешно без срабатывания суточного ограничения

### Requirement: Инициация отложенного удаления персонажа
Эндпоинт `DELETE /api/v1/shards/:shardId/characters/:characterId` SHALL переводить персонажа в `pending_deletion` с `deleteScheduledAt`: 600 с для новичков (`playtimeSeconds < 3600` и сумма навыков ≤ 150.0) и 259 200 с (72 ч) для развитых персонажей (настраивается шардом). Операция MUST отклоняться для онлайн-персонажа, `staff_locked` или при срабатывании предохранителя удаления.

#### Scenario: Отложенное удаление нового персонажа с коротким грейс-периодом
- **WHEN** игрок инициирует удаление офлайн-персонажа с `playtimeSeconds: 600` и суммой навыков `100.0`
- **THEN** система возвращает HTTP `200`, переводит статус в `pending_deletion`, устанавливает `deleteScheduledAt = now + 600s` и аннулирует непогашенные тикеты персонажа

#### Scenario: Отложенное удаление развитого персонажа с 72-часовым грейс-периодом
- **WHEN** игрок инициирует удаление офлайн-персонажа с `playtimeSeconds: 7200` или суммой навыков `220.0`
- **THEN** система устанавливает `deleteScheduledAt = now + 259200s` (72 часа) и сохраняет слот и имя за персонажем до финализации

#### Scenario: Запрет удаления персонажа, находящегося в мире
- **WHEN** игрок пытается удалить персонажа, имеющего активную игровую сессию или находящегося в 5-минутном окне задержки выхода
- **THEN** система отклоняет запрос с HTTP `409` и кодом `CHARACTER_CURRENTLY_ONLINE`

#### Scenario: Запрет удаления при блокировке доменным предохранителем
- **WHEN** подключённый доменный предохранитель удаления сообщает о непереданном имуществе или правах (например, дом или лидерство в гильдии)
- **THEN** система отклоняет запрос с HTTP `409`, кодом `CHARACTER_DELETION_BLOCKED` и структурированной причиной блокировки

### Requirement: Отмена отложенного удаления персонажа
Пока персонаж находится в статусе `pending_deletion` и текущее время строго меньше `deleteScheduledAt`, владелец аккаунта SHALL иметь возможность вызвать `POST /api/v1/shards/:shardId/characters/:characterId/cancel-delete`, полностью восстанавливая предыдущий игровой статус (`active` или `rename_required`) без потери данных, слота или имени.

#### Scenario: Успешная отмена отложенного удаления до дедлайна
- **WHEN** игрок вызывает `cancel-delete` для персонажа в статусе `pending_deletion` за 2 часа до `deleteScheduledAt`
- **THEN** система возвращает HTTP `200`, очищает `deleteScheduledAt`, возвращает исходный статус `active` и вновь разрешает выдачу игровых тикетов

#### Scenario: Попытка отмены для уже финализированного или активного персонажа
- **WHEN** игрок вызывает `cancel-delete` для персонажа в статусе `active` или после того, как персонаж финализирован в `deleted`
- **THEN** система возвращает HTTP `409` с кодом `CHARACTER_NOT_PENDING_DELETION`

### Requirement: Финализация удаления и освобождение слота и имени
По достижении `now >= deleteScheduledAt` идемпотентный обработчик SHALL переводить персонажа в статус `deleted` (надгробие хранится 90 дней для аудита и восстановления), освобождать `slotIndex` и снимать блокировку имени. Имя развитого персонажа MUST удерживаться 24 часа против перехвата чужими аккаунтами, оставаясь сразу доступным прежнему владельцу.

#### Scenario: Автоматическая финализация по истечении грейс-периода
- **WHEN** текущее время достигает `deleteScheduledAt` для персонажа в статусе `pending_deletion`
- **THEN** статус переходит в `deleted`, `slotIndex` освобождается, счётчик `usedSlots` аккаунта уменьшается на 1 и серийник персонажа остаётся закреплённым за архивной записью (не переиспользуется)

#### Scenario: Удержание имени развитого персонажа от перехвата на 24 часа
- **WHEN** развитый персонаж с именем `Aldric` финализирован в `deleted`, и через 2 часа другой аккаунт пытается создать персонажа `Aldric`
- **THEN** создание для чужого аккаунта отклоняется с HTTP `409` (`CHARACTER_NAME_RESERVED`), тогда как исходный владелец может занять `Aldric` немедленно

#### Scenario: Идемпотентность повторного запуска обработчика финализации
- **WHEN** два экземпляра фонового обработчика одновременно выбирают одного и того же персонажа для финализации
- **THEN** переход в `deleted` выполняется ровно один раз без дублирования событий аудита и без ошибок целостности

### Requirement: Контролируемое переименование персонажа с историей имён
Эндпоинт `POST /api/v1/shards/:shardId/characters/:characterId/rename` SHALL менять имя офлайн-персонажа по правилам валидации и уникальности шарда. Смена MUST разрешаться без кулдауна при `rename_required` либо по `renamePolicy` шарда (`cooldown` — 2 592 000 с / 30 дней, `token_only`, `disabled`). Старое имя MUST попадать в историю и удерживаться 24 часа для защиты от перехвата.

#### Scenario: Обязательное переименование при статусе rename_required
- **WHEN** игрок отправляет валидное свободное имя для офлайн-персонажа со статусом `rename_required`
- **THEN** система обновляет имя, переводит статус в `active`, записывает старое имя в историю имён и возвращает HTTP `200`

#### Scenario: Добровольное переименование при активном кулдауне
- **WHEN** игрок пытается добровольно переименовать персонажа через 10 дней после предыдущего переименования при политике `cooldown: 2592000s`
- **THEN** система отклоняет запрос с HTTP `429`, кодом `CHARACTER_RENAME_COOLDOWN_ACTIVE` и датой `renameAvailableAt`

#### Scenario: Отказ переименования персонажа, находящегося онлайн
- **WHEN** игрок запрашивает переименование персонажа, у которого открыта активная игровая сессия
- **THEN** система отклоняет запрос с HTTP `409` и кодом `CHARACTER_CURRENTLY_ONLINE`

#### Scenario: Запрет добровольного переименования при политике disabled
- **WHEN** на шарде установлена `renamePolicy: "disabled"` и игрок пытается переименовать персонажа в статусе `active`
- **THEN** система возвращает HTTP `403` с кодом `CHARACTER_RENAME_DISABLED`

### Requirement: Принудительное переименование и блокировка персонажа персоналом
Персонал уровня `AccessLevel >= GameMaster` SHALL иметь административные эндпоинты для перевода персонажа в `rename_required` (с обязательной причиной) и блокировки/разблокировки (`staff_locked` ↔ `active`). Любая из этих операций MUST записывать событие аудита, немедленно отзывать непогашенные игровые тикеты персонажа и публиковать уведомление в шину событий для обработки активной игровой сессии.

#### Scenario: Принудительное назначение переименования сотрудником GameMaster
- **WHEN** сотрудник уровня `GameMaster` вызывает `POST /api/v1/admin/shards/:shardId/characters/:characterId/force-rename` с причиной нарушения правил именования
- **THEN** персонаж переходит в `rename_required`, непогашенные тикеты отзываются, публикуется событие принудительного переименования и фиксируется запись аудита

#### Scenario: Блокировка персонажа с указанием причины
- **WHEN** сотрудник уровня `GameMaster` переводит персонажа в `staff_locked` с причиной расследования инцидента
- **THEN** персонаж отображается в ростере игрока со статусом `staff_locked`, попытки входа и удаления отклоняются кодом `CHARACTER_LOCKED`, а непогашенные тикеты отзываются

#### Scenario: Запрет административных операций ростера для Counselor и Player
- **WHEN** аккаунт уровня `Counselor` пытается заблокировать персонажа
- **THEN** система возвращает HTTP `403` с кодом `FORBIDDEN_INSUFFICIENT_ACCESS_LEVEL`

### Requirement: Восстановление удалённого персонажа персоналом
Персонал уровня `AccessLevel >= GameMaster` SHALL иметь возможность восстановить персонажа из статуса `deleted` в пределах 90-дневного окна хранения при наличии свободного слота у аккаунта (уровень `Administrator` MAY выполнить восстановление с расширением лимита до потолка 7). Если прежнее имя уже занято другим персонажем, восстановленный персонаж MUST получить временное уникальное имя и статус `rename_required`.

#### Scenario: Восстановление удалённого персонажа со свободным именем и слотом
- **WHEN** `GameMaster` восстанавливает персонажа, удалённого 14 дней назад, при наличии свободного слота и свободного имени
- **THEN** персонаж возвращается в статус `active` с прежним именем, прежним серийником и новым свободным `slotIndex`

#### Scenario: Восстановление персонажа при занятом прежнем имени
- **WHEN** `GameMaster` восстанавливает персонажа `Kael`, но имя `Kael` уже занято другим игроком
- **THEN** персонаж восстанавливается со статусом `rename_required` и сгенерированным уникальным временным именем, обязывая владельца выбрать новое имя перед входом

#### Scenario: Отказ восстановления по истечении 90-дневного окна хранения
- **WHEN** сотрудник пытается восстановить персонажа, финализированного 95 дней назад
- **THEN** система отклоняет запрос с HTTP `410` и кодом `CHARACTER_RESTORE_WINDOW_EXPIRED`

### Requirement: Строгая изоляция ростера между аккаунтами и шардами
Все пользовательские операции чтения и модификации ростера MUST выполняться строго в контексте пары `(accountId из токена, shardId из пути)`. Попытка обычного игрока обратиться к персонажу чужого аккаунта или к персонажу своего аккаунта через идентификатор другого шарда MUST возвращать HTTP `404` (`CHARACTER_NOT_FOUND`) без раскрытия факта существования сущности.

#### Scenario: Попытка удалить чужого персонажа по его UUID
- **WHEN** игрок B отправляет `DELETE /api/v1/shards/britannia-eu/characters/:charOfPlayerA`
- **THEN** система возвращает HTTP `404` с кодом `CHARACTER_NOT_FOUND` и не изменяет состояние персонажа игрока A

#### Scenario: Попытка переименовать своего персонажа через путь другого шарда
- **WHEN** игрок A отправляет запрос переименования своего персонажа с шарда `shard-1` по пути `/api/v1/shards/shard-2/characters/:charId/rename`
- **THEN** система возвращает HTTP `404` с кодом `CHARACTER_NOT_FOUND`
