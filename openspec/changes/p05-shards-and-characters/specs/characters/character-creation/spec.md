# Спецификация: characters/character-creation

## Purpose

Определяет серверно-авторитарный процесс создания нового персонажа по правилам эпохи шарда Ultima Online: Renaissance: справочник доступных опций, валидацию и уникальность имени, распределение начальных статов и шаблонов навыков, проверку палитр внешности, выбор стартового города, генерацию стартового набора и атомарную аллокацию серийника.

## ADDED Requirements

### Requirement: Справочник опций создания персонажа для конкретного шарда
Система SHALL предоставлять эндпоинт `GET /api/v1/shards/:shardId/character-creation-options`, возвращающий актуальные параметры создания персонажа для шарда: пул и границы начальных статов, пул и ограничения начальных навыков, список разрешённых навыков и шаблонов профессий, допустимые расы, полы, палитры внешности (кожа, волосы, борода, одежда) и список стартовых городов.

#### Scenario: Получение опций создания для стандартного UO:R шарда
- **WHEN** клиент запрашивает `GET /api/v1/shards/britannia-eu/character-creation-options`
- **THEN** система возвращает HTTP `200` с `statPool: 80`, `statMin: 10`, `statMax: 60`, `skillPoolTenths: 1000`, `maxStartingSkillTenths: 500`, списком из 6 шаблонов профессий, расой `["human"]` и 8 городами Британии

#### Scenario: Получение опций создания для шарда синтетического мира разработки
- **WHEN** клиент запрашивает опции создания для шарда с профилем ассетов `synthetic_dev`
- **THEN** система возвращает стартовый город `synthetic_haven` вместо городов проприетарной карты при сохранении правил статов и навыков UO:R

#### Scenario: Отказ при закрытом создании персонажей на шарде
- **WHEN** на шарде установлен флаг `characterCreationEnabled: false`
- **THEN** справочник возвращает `creationEnabled: false`, а попытка `POST /api/v1/shards/:shardId/characters` отклоняется с HTTP `403` и кодом `SHARD_CHARACTER_CREATION_DISABLED`

### Requirement: Валидация формата, нормализации и запрещённых паттернов имени
Имя MUST содержать 2–16 символов (`A-Za-z`, одиночный пробел, `'` или `-`), начинаться и заканчиваться буквой, без двойных пробелов, подряд идущей пунктуации, управляющих символов и смешанных алфавитов. Запрещённая лексика, имена лора и служебные префиксы (`GM`, `Admin`, `Seer`, `Counselor`, `Developer`, `Owner`, `Staff`, `System`) MUST отклоняться (кроме `Administrator`).

#### Scenario: Предварительная проверка валидного имени через эндпоинт валидации
- **WHEN** игрок вызывает `POST /api/v1/shards/britannia-eu/characters/validate-name` с именем `Elara D'Vane`
- **THEN** система возвращает HTTP `200` с `{ valid: true, available: true, normalizedName: "elara d'vane" }`

#### Scenario: Отклонение имени со служебным префиксом или запрещёнными символами
- **WHEN** игрок передаёт имя `GM Aldric`, `Hero_123`, `A` или имя с невидимым zero-width символом
- **THEN** система возвращает ошибку валидации с кодом `INVALID_CHARACTER_NAME` и конкретной причиной (`RESERVED_PREFIX`, `DISALLOWED_CHARACTERS`, `LENGTH_OUT_OF_RANGE`)

#### Scenario: Отклонение имени из списка нецензурных или зарезервированных имён лора
- **WHEN** обычный игрок пытается создать персонажа с именем `Lord British` или словом из словаря запрещённой лексики
- **THEN** система отклоняет запрос с HTTP `422` и кодом `CHARACTER_NAME_FORBIDDEN`

#### Scenario: Ограничение частоты предварительных проверок имени
- **WHEN** аккаунт отправляет более 30 запросов `POST .../validate-name` за 60 секунд
- **THEN** система возвращает HTTP `429` с кодом `NAME_VALIDATION_RATE_LIMITED` и заголовком `Retry-After`

### Requirement: Уникальность имени на шарде и защита от гонок и перехвата
Имя персонажа MUST быть уникально в пределах одного шарда без учёта регистра (`normalizedName`) среди всех не удалённых персонажей и активных 24-часовых резерваций после удаления или переименования (для чужих аккаунтов). При одновременной отправке двух запросов создания с одинаковым именем ровно один MUST завершиться успешно, а второй — HTTP `409` (`CHARACTER_NAME_TAKEN`).

#### Scenario: Отклонение дубликата имени в другом регистре на том же шарде
- **WHEN** на шарде существует персонаж `Kaelen`, а другой игрок пытается создать `kaelen` или `KAELEN`
- **THEN** система отклоняет создание с HTTP `409` и кодом `CHARACTER_NAME_TAKEN`

#### Scenario: Разрешение одинакового имени на разных шардах
- **WHEN** персонаж `Kaelen` существует на шарде `britannia-eu`, а игрок создаёт `Kaelen` на шарде `siege-eu`
- **THEN** создание на `siege-eu` выполняется успешно с HTTP `201`

#### Scenario: Конкурентное создание с одинаковым именем двумя аккаунтами
- **WHEN** два аккаунта одновременно отправляют `POST /api/v1/shards/britannia-eu/characters` с именем `Rowan`
- **THEN** ровно один запрос получает HTTP `201`, а второй получает HTTP `409` (`CHARACTER_NAME_TAKEN`) без создания дубликата

### Requirement: Распределение начальных характеристик и расчёт производных показателей
Начальные характеристики `str`, `dex`, `int` MUST быть целыми числами в диапазоне `[creationStatMin, creationStatMax]` (для UO:R `[10, 60]`), а их сумма MUST строго равняться `creationStatPool` (для UO:R `80`). Система SHALL детерминированно вычислять производные показатели по каноническим формулам UO:R: `maxHits = 50 + floor(str / 2)`, `maxStam = dex`, `maxMana = int`, `maxWeight = 40 + floor(3.5 * str)`.

#### Scenario: Валидное распределение 80 очков статов и расчёт виталов
- **WHEN** игрок создаёт персонажа с `str: 45, dex: 25, int: 10`
- **THEN** система сохраняет `maxHits: 72`, `hits: 72`, `maxStam: 25`, `stam: 25`, `maxMana: 10`, `mana: 10` и `maxWeight: 197`

#### Scenario: Отклонение суммы статов, не равной пулу шарда
- **WHEN** клиент отправляет `str: 50, dex: 30, int: 10` (сумма 90 вместо 80)
- **THEN** система отклоняет запрос с HTTP `422` и кодом `INVALID_STAT_ALLOCATION`

#### Scenario: Отклонение характеристики ниже минимума или выше максимума
- **WHEN** клиент отправляет `str: 65, dex: 10, int: 5` (выход за пределы `[10, 60]`)
- **THEN** система отклоняет запрос с HTTP `422` и кодом `INVALID_STAT_ALLOCATION`

### Requirement: Шаблоны профессий и пользовательское распределение навыков UO:R
Создание персонажа SHALL поддерживать выбор шаблона профессии (Warrior, Mage, Blacksmith, Bard, Ranger, Tamer) или режим `advanced`. В режиме `advanced` игрок выбирает до 3 различных разрешённых навыков из 49 навыков UO:R (исключая запрещённые на старте `stealth` и `remove_trap`), каждый в диапазоне `0..500` десятых (`0.0..50.0`) при точной сумме `1000` (`100.0`); все 49 навыков инициализируются с замком `up`.

#### Scenario: Создание по пресету профессии Mage
- **WHEN** игрок выбирает `professionId: "mage"` без ручной переоценки
- **THEN** система назначает канонические статы (`str: 25, dex: 10, int: 45`) и стартовые навыки шаблона (`magery: 500`, `meditation: 300`, `eval_int: 200`), а остальные 46 навыков устанавливает в `0` с замком `up`

#### Scenario: Создание в режиме advanced со сборкой 50.0 / 50.0
- **WHEN** игрок выбирает `professionId: "advanced"` с навыками `[{ skill: "magery", valueTenths: 500 }, { skill: "resisting_spells", valueTenths: 500 }]`
- **THEN** система принимает сборку (сумма `1000`, максимум `500` на навык) и инициализирует все 49 навыков персонажа

#### Scenario: Отклонение запрещённого стартового навыка или дубликата навыка
- **WHEN** игрок передаёт в `advanced` навык `stealth` или дважды указывает `swordsmanship`, либо сумму `1050`
- **THEN** система отклоняет запрос с HTTP `422` и кодом `INVALID_SKILL_ALLOCATION`

### Requirement: Валидация расы, пола, модели тела и палитр внешности
Система MUST проверять внешность по белым спискам шарда: в UO:R допустима раса `human`, пол `male` (Body `400`) или `female` (Body `401`), `skinHue` `1002..1058`, `hairStyle` из списка UO:R (или `0`), `hairHue` `1102..1149` (`0` при лысине), `facialHairStyle` только для `male`, `facialHairHue` `1102..1149` (`0` без бороды), `shirtHue` и `pantsHue` `2..1001`.

#### Scenario: Создание мужского персонажа с валидной внешностью и бородой
- **WHEN** игрок передаёт `race: "human"`, `gender: "male"`, `skinHue: 1020`, `hairStyle: 8251`, `hairHue: 1109`, `facialHairStyle: 8254`, `facialHairHue: 1109`, `shirtHue: 100`, `pantsHue: 250`
- **THEN** система назначает `body: 400` и сохраняет указанные параметры внешности

#### Scenario: Запрет бороды у женского персонажа
- **WHEN** клиент передаёт `gender: "female"` и `facialHairStyle: 8254`
- **THEN** система отклоняет запрос с HTTP `422` и кодом `INVALID_APPEARANCE`

#### Scenario: Запрет недопустимых редких или служебных хью
- **WHEN** клиент пытается передать `skinHue: 1153` или `shirtHue: 2048` вне разрешённых стартовых палитр
- **THEN** система отклоняет запрос с HTTP `422` и кодом `INVALID_APPEARANCE`

### Requirement: Выбор стартового города и серверное назначение координат спавна
Клиент MUST передавать только идентификатор стартового города `startingCityId` из каталога разрешённых городов шарда. Сервер SHALL авторитарно назначать координаты `(facet, x, y, z)` по конфигурации города и типу PvP шарда (`trammel` для `renaissance_split` и `trammel_only`, `felucca` для `felucca_only` и `siege_perilous`) и MUST отклонять или игнорировать любые переданные клиентом координаты.

#### Scenario: Назначение координат Britain в Trammel на стандартном шарде
- **WHEN** игрок выбирает `startingCityId: "britain"` на шарде типа `renaissance_split`
- **THEN** сервер назначает персонажу фасет `trammel` и серверные координаты гостиницы Britain без участия клиента

#### Scenario: Назначение координат в Felucca на шарде Siege Perilous
- **WHEN** игрок выбирает `startingCityId: "britain"` на шарде типа `siege_perilous`
- **THEN** сервер назначает персонажу фасет `felucca` и соответствующие стартовые координаты в Felucca

#### Scenario: Отклонение несуществующего или отключённого стартового города
- **WHEN** клиент передаёт `startingCityId: "delucia"` на шарде, где этот город не входит в список стартовых
- **THEN** система отклоняет запрос с HTTP `422` и кодом `INVALID_STARTING_CITY`

### Requirement: Детерминированный дескриптор стартового набора экипировки
При создании персонажа система SHALL детерминированно вычислять и сохранять неизменяемый дескриптор `starterLoadout` (версия схемы, базовая одежда новичка с выбранными `shirtHue`/`pantsHue`, обувь, рюкзак, кинжал, стартовое золото правила шарда и профильные предметы за каждый стартовый навык ≥ `30.0`, помеченные `newbied: true`) с флагом `starterLoadoutGranted: false` для последующей атомарной материализации при первом входе в мир.

#### Scenario: Формирование стартового набора для мага с навыком Magery 50.0
- **WHEN** создаётся персонаж с `magery: 500`, `shirtHue: 50`, `pantsHue: 60`
- **THEN** сохранённый `starterLoadout` содержит одежду с хью `50`/`60`, стартовое золото, книгу заклинаний новичка и базовый набор реагентов с флагом `starterLoadoutGranted: false`

#### Scenario: Формирование стартового набора без дублирования при нескольких боевых навыках
- **WHEN** игрок создаёт персонажа со стартовыми навыками `swordsmanship: 500` и `tactics: 500`
- **THEN** дескриптор содержит ровно один рюкзак, один базовый комплект одежды и профильный набор мечника без дублирования базовых предметов

### Requirement: Атомарная персистенция, аллокация серийника и идемпотентность
Эндпоинт `POST /api/v1/shards/:shardId/characters` MUST в одной транзакции под блокировкой пары `(accountId, shardId)` проверить квоту слотов и анти-флуд лимит, зарезервировать имя, выделить уникальный 32-битный серийник мобайла в диапазоне `0x00000001..0x3FFFFFFF` для данного шарда, назначить минимальный свободный `slotIndex` и сохранить персонажа и 49 навыков. Поддерживается заголовок `Idempotency-Key` (TTL 300 с).

#### Scenario: Успешная атомарная аллокация серийника и первого свободного слота
- **WHEN** аккаунт со слотами `[0, 2]` (слот 1 свободен) создаёт нового персонажа
- **THEN** система выделяет уникальный `serial` в поддиапазоне персонажей игроков `0x00000001..0x1FFFFFFF` (NPC используют `0x20000000..0x3FFFFFFF`), назначает `slotIndex: 1`, сохраняет все 49 записей навыков и возвращает HTTP `201`

#### Scenario: Безопасный повтор запроса с тем же Idempotency-Key
- **WHEN** клиент повторяет идентичный запрос создания с тем же заголовком `Idempotency-Key` в течение 300 секунд после обрыва связи
- **THEN** система не создаёт второго персонажа и не возвращает `CHARACTER_NAME_TAKEN`, а возвращает исходный ответ HTTP `201` с тем же `characterId` и `serial`

#### Scenario: Конфликт при повторном использовании Idempotency-Key с другим телом запроса
- **WHEN** клиент отправляет тот же `Idempotency-Key`, но с другим именем или параметрами персонажа
- **THEN** система отклоняет запрос с HTTP `422` и кодом `IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`

#### Scenario: Защита от гонки обхода лимита слотов при параллельных запросах
- **WHEN** аккаунт с 4 из 5 занятых слотов отправляет два параллельных запроса создания с разными валидными именами
- **THEN** ровно один запрос завершается HTTP `201` (слот 4), а второй — HTTP `409` (`CHARACTER_SLOT_LIMIT_REACHED`)

### Requirement: Соответствие всех правил создания профилю эпохи шарда
Все параметры валидации создания персонажа (пул и границы статов, пул и максимум навыков, список запрещённых стартовых навыков, допустимые расы, стартовые города, целевой фасет, стартовое золото и лимит слотов) MUST разрешаться динамически из профиля эпохи и конфигурации конкретного шарда, обеспечивая одновременную работу шардов с разными наборами правил в рамках одного развёртывания.

#### Scenario: Одновременная работа UO:R и кастомного тестового шарда
- **WHEN** в одном развёртывании активны шард `britannia-eu` (статы 80, слотов 5, Trammel) и `siege-eu` (статы 80, слотов 1, Felucca)
- **THEN** создание персонажа на каждом шарде применяет строго его профиль эпохи и конфигурации без взаимного влияния

#### Scenario: Отклонение расширенной расы на шарде без соответствующего флага эпохи
- **WHEN** клиент отправляет `race: "elf"` на шард UO:R, где флаг профиля эпохи `elvesEnabled` (P01) равен `false`
- **THEN** система отклоняет запрос с HTTP `422` и кодом `UNSUPPORTED_RACE_FOR_SHARD_ERA`
