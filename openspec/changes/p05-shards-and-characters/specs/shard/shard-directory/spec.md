# Спецификация: shard/shard-directory

## Purpose

Определяет каталог игровых шардов UO3: список доступных миров, их правила (тип PvP, профиль эпохи, активные фасеты), расчёт живого статуса и онлайна по сигналам игровых узлов, проверку совместимости протокола, видимость по уровню доступа и административное управление реестром.

## ADDED Requirements

### Requirement: Каталог публичных шардов и их базовые метаданные
Система SHALL предоставлять эндпоинт `GET /v1/shards`, возвращающий упорядоченный список доступных шардов со стабильным идентификатором, уникальным slug, отображаемым именем, регионом, часовым поясом, типом PvP (`renaissance_split`, `felucca_only`, `trammel_only`, `siege_perilous`), идентификатором эпохи, списком активных фасетов, текущим статусом, онлайном и вместимостью.

#### Scenario: Получение списка публичных шардов без аутентификации
- **WHEN** неаутентифицированный клиент отправляет запрос `GET /v1/shards`
- **THEN** система возвращает HTTP `200` со списком только публичных неархивных шардов
- **AND** для каждого шарда отсутствуют персональные поля аккаунта (`myCharacterCount` и `entryEligibility`)

#### Scenario: Устойчивый порядок шардов в каталоге
- **WHEN** в каталоге зарегистрировано несколько публичных шардов с различными приоритетами отображения и именами
- **THEN** система возвращает их отсортированными по возрастанию `displayOrder`, а при совпадении — лексикографически по `slug`

#### Scenario: Исключение архивных шардов из основного списка
- **WHEN** администратор переводит шард в архивный статус `archived`
- **THEN** данный шард не включается в выдачу `GET /v1/shards` для обычных игроков

### Requirement: Персональный контекст игрока в каталоге шардов
При наличии валидного токена доступа в запросе `GET /v1/shards` система SHALL обогащать каждую запись шарда количеством не удалённых персонажей данного аккаунта (`myCharacterCount`), максимально доступным числом слотов (`maxCharacterSlots`) и признаком допустимости входа (`canEnter`, `blockReason`).

#### Scenario: Обогащение списка данными аутентифицированного игрока
- **WHEN** аутентифицированный игрок с 2 активными персонажами на шарде `britannia-eu` запрашивает `GET /v1/shards`
- **THEN** система возвращает HTTP `200`, где для `britannia-eu` указано `myCharacterCount: 2`, `maxCharacterSlots: 5` и `canEnter: true`

#### Scenario: Отображение причины недоступности входа при активной блокировке шарда
- **WHEN** аутентифицированный игрок имеет локальную блокировку на конкретном шарде и запрашивает `GET /v1/shards`
- **THEN** шард присутствует в списке с `canEnter: false` и кодом `blockReason: "SHARD_ACCOUNT_BANNED"`

#### Scenario: Отклонение запроса с просроченным токеном доступа
- **WHEN** клиент передаёт заголовок `Authorization` с истёкшим или повреждённым токеном доступа
- **THEN** система возвращает HTTP `401` с кодом ошибки `AUTH_TOKEN_INVALID` вместо тихого отката к анонимному ответу

### Requirement: Видимость скрытых и служебных шардов по уровню доступа
Каждый шард MUST иметь политику видимости (`public`, `unlisted`, `staff_only`, `beta_whitelist`) и минимальный уровень доступа для видимости и входа. Шарды с политикой `staff_only` и `beta_whitelist` MUST не раскрываться неавторизованным пользователям ни в списке, ни при прямом запросе по идентификатору.

#### Scenario: Скрытие служебного шарда от обычного игрока
- **WHEN** игрок с уровнем доступа `Player` запрашивает `GET /v1/shards` или `GET /v1/shards/qa-internal` для шарда с `visibility: "staff_only"`
- **THEN** шард отсутствует в общем списке, а прямой запрос возвращает HTTP `404` с кодом `SHARD_NOT_FOUND`

#### Scenario: Отображение служебного шарда персоналу
- **WHEN** сотрудник с уровнем доступа `Counselor` или выше запрашивает `GET /v1/shards`
- **THEN** система включает в ответ шарды с `visibility: "staff_only"`, помеченные флагом `visibility: "staff_only"`

#### Scenario: Доступ к скрытому по ссылке шарду по точному идентификатору
- **WHEN** аутентифицированный игрок запрашивает `GET /v1/shards/event-arena` для шарда с `visibility: "unlisted"`
- **THEN** шард не отображается в `GET /v1/shards`, но прямой запрос по идентификатору возвращает HTTP `200` с его карточкой

### Requirement: Детальная карточка шарда и сводка правил эпохи
Система SHALL предоставлять эндпоинт `GET /v1/shards/:shardId`, возвращающий полную конфигурацию правил шарда: параметры профиля эпохи (кап статов 225, кап навыков 700.0, максимум навыка 100.0 по умолчанию для UO:R), лимит персонажей на аккаунт, политику переименования, список разрешённых фасетов, описание PvP-режима и активное объявление о техработах.

#### Scenario: Запрос карточки стандартного UO:R шарда
- **WHEN** клиент запрашивает `GET /v1/shards/britannia-eu`
- **THEN** система возвращает HTTP `200` с `pvpType: "renaissance_split"`, фасетами `["felucca", "trammel"]`, `statCap: 225`, `skillCapTenths: 7000`, `maxSingleSkillTenths: 1000` и `maxCharactersPerAccount: 5`

#### Scenario: Запрос карточки шарда режима Siege Perilous
- **WHEN** клиент запрашивает карточку шарда с типом `siege_perilous`
- **THEN** система возвращает `facets: ["felucca"]`, `maxCharactersPerAccount: 1` и явный флаг `rulesetFlags.singleCharacterShard: true`

#### Scenario: Запрос несуществующего шарда
- **WHEN** клиент запрашивает `GET /v1/shards/unknown-shard`
- **THEN** система возвращает HTTP `404` с кодом ошибки `SHARD_NOT_FOUND`

### Requirement: Агрегация живого состояния и онлайна через heartbeat
Игровые узлы шарда MUST публиковать периодические сигналы жизнеспособности каждые 5 секунд с TTL 15 секунд, содержащие число активных игроков, число зарезервированных мест, вместимость партиций, p99 длительности тика и флаг дренажа. Каталог SHALL агрегировать живой онлайн по всем активным партициям и автоматически переводить шард в эффективный статус `offline` при истечении всех heartbeat.

#### Scenario: Корректная агрегация онлайна по нескольким партициям
- **WHEN** две активные партиции одного шарда публикуют свежие heartbeat со значениями онлайна 320 и 480 при лимите 2000
- **THEN** каталог возвращает для шарда `status: "online"` и `onlineCount: 800`

#### Scenario: Автоматический переход в offline при потере сигналов узлов
- **WHEN** ни один игровой узел шарда не обновлял heartbeat более 15 секунд, а шард не переведён вручную в `maintenance`
- **THEN** каталог возвращает эффективный статус `offline`, `onlineCount: 0` и `canEnter: false` с причиной `SHARD_OFFLINE`

#### Scenario: Переход в degraded при деградации тика игрового узла
- **WHEN** активный узел шарда сообщает о превышении целевого бюджета тика (`tickP99Ms > 45` при целевом тике 50 мс) в двух последовательных heartbeat
- **THEN** каталог отображает эффективный статус `degraded`, сохраняя возможность входа и публикуя флаг повышенной задержки

### Requirement: Расчёт индикатора загрузки и ограничение входа при заполнении
Система SHALL рассчитывать уровень загрузки шарда как отношение `(onlineCount + reservedSeats)` к `hardCapacity`: `low` (< 50%), `medium` (50–79%), `high` (80–99%), `full` (≥ 100%). При статусе `full` вход для уровня `Player` MUST блокироваться с причиной `SHARD_FULL`, тогда как для персонала (`Counselor` и выше) SHALL действовать выделенный буфер вместимости (по умолчанию +50 слотов).

#### Scenario: Расчёт уровня загрузки при 85% заполнении
- **WHEN** шард с `hardCapacity: 2000` имеет `onlineCount: 1650` и `reservedSeats: 50`
- **THEN** каталог возвращает `loadTier: "high"` и `canEnter: true` для обычного игрока

#### Scenario: Достижение предела вместимости для обычного игрока
- **WHEN** шард с `hardCapacity: 2000` достигает `onlineCount + reservedSeats >= 2000`
- **THEN** каталог возвращает `loadTier: "full"`, а для аккаунта `Player` выставляет `canEnter: false` и `blockReason: "SHARD_FULL"`

#### Scenario: Обход заполнения для сотрудника персонала в пределах буфера
- **WHEN** шард имеет `loadTier: "full"` (2000 из 2000), но занято менее 50 слотов буфера персонала
- **THEN** для аккаунта с уровнем `GameMaster` каталог возвращает `canEnter: true`

### Requirement: Режимы технического обслуживания и планового дренажа
Администратор (`AccessLevel >= Administrator`) SHALL иметь возможность переводить шард в режим `maintenance` (с необязательным локализованным сообщением и прогнозом `estimatedResumeAt`) или `draining` (запрет новых входов для игроков при завершении текущих сессий). В режиме `maintenance` доступ к входу MUST быть разрешён только персоналу уровня не ниже `maintenanceBypassLevel` (по умолчанию `GameMaster`).

#### Scenario: Перевод шарда в техническое обслуживание с указанием ETA
- **WHEN** администратор переводит шард в статус `maintenance` с причиной и `estimatedResumeAt`
- **THEN** каталог немедленно возвращает `status: "maintenance"`, текст объявления, `estimatedResumeAt` и `canEnter: false` (`SHARD_IN_MAINTENANCE`) для игроков `Player`

#### Scenario: Доступ GameMaster в режиме обслуживания
- **WHEN** шард находится в статусе `maintenance` с `maintenanceBypassLevel: "GameMaster"`
- **THEN** для аккаунта уровня `GameMaster` каталог возвращает `canEnter: true`, а для `Counselor` — `canEnter: false`

#### Scenario: Режим планового дренажа перед перезапуском
- **WHEN** шард переведён в статус `draining`
- **THEN** каталог отображает `status: "draining"` и запрещает новые входы игрокам с причиной `SHARD_DRAINING`, не разрывая уже открытые игровые сессии

### Requirement: Проверка совместимости версий протокола и профиля ассетов
Каждый шард MUST декларировать допустимый диапазон версий клиентского протокола (`minProtocolVersion`, `maxProtocolVersion` в формате semver) и требуемый профиль ассетов (`uo_classic_7` или `synthetic_dev`). При получении заголовка `X-UO3-Protocol-Version` каталог SHALL вычислять и возвращать флаги совместимости `protocolCompatible` и `upgradeRequired`.

#### Scenario: Совместимая версия протокола клиента
- **WHEN** шард требует диапазон `>=1.0.0 <=1.2.99`, а клиент передаёт `X-UO3-Protocol-Version: 1.1.0`
- **THEN** каталог возвращает `protocolCompatible: true` и `upgradeRequired: false`

#### Scenario: Устаревшая версия протокола клиента
- **WHEN** клиент передаёт `X-UO3-Protocol-Version: 0.9.5`, что ниже `minProtocolVersion: 1.0.0`
- **THEN** каталог возвращает `protocolCompatible: false`, `upgradeRequired: true` и `canEnter: false` с `blockReason: "PROTOCOL_VERSION_UNSUPPORTED"`

#### Scenario: Некорректный формат заголовка версии протокола
- **WHEN** клиент передаёт невалидную строку `X-UO3-Protocol-Version: latest`
- **THEN** система возвращает HTTP `400` с кодом ошибки `INVALID_PROTOCOL_VERSION_HEADER`

### Requirement: Кэширование, задержки ответа и деградация при сбое кэша
Эндпоинт `GET /v1/shards` SHALL поддерживать условное кэширование (`ETag` / `If-None-Match`) с коротким `Cache-Control` (5 секунд) и обеспечивать p95 времени ответа ≤ 50 мс при штатной работе. При временной недоступности хранилища живых heartbeat система MUST деградировать контролируемо: возвращать метаданные шардов со статусом `degraded`, `onlineCount: null` и запретом входа (`SHARD_TELEMETRY_UNAVAILABLE`).

#### Scenario: Возврат 304 Not Modified при совпадении ETag
- **WHEN** клиент повторяет запрос `GET /v1/shards` с заголовком `If-None-Match`, совпадающим с текущим `ETag`
- **THEN** система возвращает HTTP `304` без тела ответа

#### Scenario: Деградация при недоступности хранилища heartbeat
- **WHEN** хранилище оперативных heartbeat временно недоступно при обработке `GET /v1/shards`
- **THEN** система возвращает HTTP `200` с метаданными шардов из основного хранилища, `status: "degraded"`, `onlineCount: null` и `canEnter: false` (`SHARD_TELEMETRY_UNAVAILABLE`)

### Requirement: Административное управление реестром шардов
Система SHALL предоставлять защищённые эндпоинты (`POST /v1/admin/shards`, `PATCH /v1/admin/shards/:shardId`, `POST /v1/admin/shards/:shardId/status`), доступные только для `AccessLevel >= Administrator`, для регистрации, настройки и архивации шардов. Несовместимая смена эпохи на непустом шарде вне `maintenance` MUST отклоняться, а каждая мутация MUST фиксироваться в аудите.

#### Scenario: Регистрация нового шарда администратором
- **WHEN** администратор отправляет валидный запрос `POST /v1/admin/shards` с уникальным `slug` и конфигурацией UO:R
- **THEN** система создаёт шард со статусом `offline`, возвращает HTTP `201` и публикует событие аудита `shard.created`

#### Scenario: Запрет несовместимой смены эпохи на работающем шарде
- **WHEN** администратор пытается изменить `eraProfileId` или уменьшить `maxCharactersPerAccount` на шарде в статусе `online`, содержащем персонажей
- **THEN** система отклоняет запрос с HTTP `409` и кодом `SHARD_MUTATION_REQUIRES_MAINTENANCE`

#### Scenario: Отказ в доступе к административным эндпоинтам не-администратору
- **WHEN** сотрудник уровня `GameMaster` или игрок `Player` отправляет `PATCH /v1/admin/shards/britannia-eu`
- **THEN** система возвращает HTTP `403` с кодом `FORBIDDEN_INSUFFICIENT_ACCESS_LEVEL`
