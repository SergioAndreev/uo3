# Спецификация: domain/ruleset-profile

## Purpose

Определяет профиль правил Duskmarch: встроенный неизменяемый профиль `duskmarch` с константами ARCHITECTURE §5, флаги функций, пресеты и переопределение на шарде с проверкой инвариантов, детерминированный отпечаток, публичный срез для клиента и базовые формулы, общие для клиента и сервера.

## ADDED Requirements

### Requirement: Встроенный профиль duskmarch
Пакет `@duskmarch/rules` MUST предоставлять глубоко замороженный профиль `duskmarch` версии `1`, значения которого совпадают с таблицей констант ARCHITECTURE §5 и таблицей профиля в design.md. Изменение любого значения по умолчанию MUST повышать версию профиля.

#### Scenario: Чтение констант
- **WHEN** запрашивается профиль `duskmarch`
- **THEN** `movement.walkMs = 360`, `movement.runMs = 220`, `skills.totalCapTenths = 6 000`, `stats.totalCap = 240`

#### Scenario: Неизменяемость
- **WHEN** код пытается изменить `stats.totalCap` профиля в строгом режиме
- **THEN** возникает `TypeError`

### Requirement: Флаги функций
Профиль MUST содержать типизированные флаги функций: `realmDusk`, `mounts`, `housing`, `seafaring`, `beaconTravel`, `playerBounties`. Неизвестный флаг в переопределении SHALL отклоняться с кодом `ERR_UNKNOWN_FEATURE_FLAG`. Новые возможности будущих фаз MUST добавляться новыми флагами, не меняя смысл существующих полей.

#### Scenario: Отключение плана Марь
- **WHEN** шард переопределяет `features.realmDusk = false`
- **THEN** итоговый профиль сообщает, что план `dusk` недоступен, а остальные флаги сохраняют значения по умолчанию

### Requirement: Пресеты и переопределение на шарде
Шард MUST выбирать пресет (`standard` или `proving`) и MAY применять частичное переопределение из JSON или YAML, проверяемое по схеме профиля. Поля, не заданные переопределением, SHALL браться из пресета. Пресет `proving` SHALL ускорять игровое время в 10 раз и разрешать только план `proving`.

#### Scenario: Пресет proving
- **WHEN** шард выбирает пресет `proving` без переопределения
- **THEN** игровой час длится `24 000 мс`, доступен только план `proving`

### Requirement: Межполевые инварианты профиля
Итоговый профиль MUST удовлетворять инвариантам: `movement.runMs < movement.walkMs`, `movement.mountedRunMs < movement.mountedWalkMs`, `stats.min × 3 ≤ stats.totalCap ≤ stats.max × 3`, `skills.maxTenths ≤ skills.totalCapTenths`, все длительности шага не меньше `tickMs`. Нарушения SHALL возвращаться одним списком с путями полей и кодом `ERR_RULESET_INVARIANT`.

#### Scenario: Сбор всех нарушений
- **WHEN** переопределение задаёт `movement.runMs = 400` и `stats.totalCap = 20`
- **THEN** применение отклоняется с `ERR_RULESET_INVARIANT` и двумя нарушениями с путями `movement.runMs` и `stats.totalCap`

#### Scenario: Корректное переопределение
- **WHEN** переопределение задаёт `limits.groundDecayMs = 1 800 000`
- **THEN** итоговый профиль содержит новое значение, остальные поля совпадают с пресетом

### Requirement: Детерминированный отпечаток профиля
Отпечаток профиля MUST вычисляться как SHA-256 канонического JSON (ключи по возрастанию, без пробелов) и записываться строкой из 64 hex-цифр. SHA-256 MUST быть изоморфной синхронной реализацией без `node:crypto`. Одинаковые профили SHALL давать одинаковый отпечаток независимо от порядка ключей во входных данных.

#### Scenario: Независимость от порядка ключей
- **WHEN** один и тот же профиль собирается из переопределений с разным порядком ключей
- **THEN** отпечатки совпадают

#### Scenario: Изменение значения
- **WHEN** в профиле меняется `movement.walkMs` с `360` на `350`
- **THEN** отпечаток меняется

### Requirement: Публичный срез для клиента
Клиент MUST получать только публичный срез профиля: движение, планы, характеристики и навыки, радиусы речи и интереса, флаги функций, версия и отпечаток. Пороги репутации, параметры распада и задержки выхода SHALL оставаться только на сервере.

#### Scenario: Отсутствие серверных полей
- **WHEN** строится публичный срез профиля `duskmarch`
- **THEN** в нём есть `movement` и `features`, но нет `reputation` и `limits`

### Requirement: Базовые формулы
Формулы MUST быть чистыми функциями профиля и характеристик: здоровье `60 + floor(Мощь × 0,6)`, запал `40 + floor(Сноровка × 0,8)`, созвучие `40 + floor(Воля × 0,8)`, переносимый вес `50 + floor(Мощь × 1,5)` кг; длительность шага по режиму и наличию верхового животного; проверка допустимости набора характеристик и суммы навыков относительно капов. Дробные коэффициенты MUST вычисляться в целых числах (сотых долях), чтобы результат совпадал на всех платформах.

#### Scenario: Ресурсы героя
- **WHEN** вычисляются ресурсы для Мощи `85`, Сноровки `90`, Воли `65`
- **THEN** здоровье `111`, запал `112`, созвучие `92`, переносимый вес `177`

#### Scenario: Превышение капа характеристик
- **WHEN** проверяется набор Мощь `100`, Сноровка `100`, Воля `41`
- **THEN** набор отклоняется: сумма `241` больше капа `240`
